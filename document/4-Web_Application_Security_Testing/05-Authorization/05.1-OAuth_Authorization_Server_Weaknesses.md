# Debilidades del servidor de autorización de OAuth

## Resumen

OAuth almacena las identidades de los usuarios y sus derechos de acceso correspondientes en el servidor de autorización (AS). El AS desempeña un papel crucial durante el flujo de OAuth, ya que otorga a los clientes acceso a los recursos. Para hacerlo de forma segura, debe validar correctamente los parámetros que forman parte del flujo de OAuth.

No validar los parámetros puede provocar la toma de control de cuentas, el acceso no autorizado a recursos y la elevación de privilegios.

## Objetivos de las pruebas

- Identificar debilidades en el servidor de autorización.

## Cómo probar

Para probar las debilidades del AS, se debe intentar:

1. Recuperar las credenciales utilizadas para la autorización.
2. Obtener acceso a recursos arbitrarios mediante navegación forzada.
3. Eludir la autorización.

### Validación insuficiente del URI de redirección

Si el `redirect_uri` no se valida correctamente, se puede crear un enlace que contenga una URL que apunte a un servidor controlado por un atacante. Esto puede utilizarse para engañar al AS y hacer que envíe un código de autorización al atacante. En el siguiente ejemplo, se utiliza `client.evil.com` como `redirect_uri` falsificado.

```text
https://as.example.com/authorize?client_id=example-client&redirect_uri=http%3A%2F%client.evil.com%2F&state=example&response_mode=fragment&response_type=code&scope=openid&nonce=example
```

Si un usuario abre este enlace en el agente de usuario, el AS redirigirá el agente de usuario a la URL maliciosa.

Un atacante puede capturar el valor `code` incluido en la URL falsificada y luego enviarlo al endpoint de token del AS.

La siguiente solicitud ilustra una solicitud de autorización que envía el `redirect_uri` al servidor de autorización. El cliente `client.example.com` envía una solicitud de autorización al AS `as.example.com` con el URI de redirección codificado en URL `http%3A%2F%2Fclient.example.com%2F`.

```http
GET /authorize
    ?redirect_uri=http%3A%2F%2Fclient.example.com%2F
    &client_id=example-client
    &errorPath=%2Ferror
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=query
    &state=example
    &nonce=example
    &code_challenge=example
    &code_challenge_method=S256 HTTP/1.1
Host: as.example.com
```

El AS responde con una redirección que contiene el código de autorización. Este código puede intercambiarse por un token de acceso mediante la solicitud de token. Como se muestra a continuación, la URL del encabezado `Location` es el URI proporcionado en el parámetro `redirect_uri` anterior.

```http
HTTP/1.1 302 Found
Date: Mon, 18 Oct 2021 20:46:44 GMT
Content-Type: text/html; charset=utf-8
Content-Length: 340
Location: https://client.example.com/?code=example&state=example
```

Para comprobar si el AS es vulnerable a una validación insuficiente del URI de redirección, capture el tráfico con un proxy de interceptación HTTP, como ZAP.

1. Inicie el flujo de OAuth y páuselo en la solicitud de autorización.
2. Cambie el valor de `redirect_uri` y observe la respuesta.
3. Examine la respuesta e identifique si el AS aceptó el parámetro `redirect_uri` arbitrario.

Si el AS redirige el agente de usuario al `redirect_uri` especificado, el AS no valida correctamente el `redirect_uri`.

Además, consulte la sección `Common Filter Bypass` de [Falsificación de solicitudes del lado del servidor](../07-Injection/19-Server-Side_Request_Forgery.md) para identificar formas habituales de eludir la validación del URI de redirección.

### Inyección de código de autorización

Durante el intercambio de código del flujo Authorization Code, el AS emite un código al cliente, que luego se intercambia en el endpoint de token para obtener un token de autorización y un token de actualización.

Realice las siguientes pruebas contra el AS:

1. Envíe un código válido para otro `client_id`.
2. Envíe un código válido para otro propietario del recurso.
3. Envíe un código válido para otro `redirect_uri`.
4. Reenvíe el código más de una vez (repetición del código).

#### Clientes públicos

La solicitud enviada al endpoint de token contiene el código de autorización. Este se intercambia por el token. Capture esta solicitud con un proxy de interceptación HTTP, como ZAP, y vuelva a enviarla con valores modificados.

```http
POST /oauth/token HTTP/1.1
Host: as.example.com
[...]

{
    "errorPath":"/error",
    "client_id":"example-client",
    "code":"INJECT_CODE_HERE",
    "grant_type":"authorization_code",
    "redirect_uri":"https://client.example.com"
}
```

Si el AS responde con un `access_token`, el código se inyectó correctamente.

#### Prueba de clientes confidenciales

Como el flujo de OAuth para clientes confidenciales está protegido adicionalmente por un secreto de cliente, no es posible enviar directamente un código de autorización al endpoint de token. En su lugar, inyecte el código de autorización en el cliente. A continuación, el cliente confidencial enviará este código inyectado en la solicitud de token junto con el secreto de cliente.

Primero, capture un código de autorización del AS:

1. Inicie el flujo de código de autorización con la usuaria Alice. Párelo cuando reciba un código del AS.
2. No envíe el código al cliente y anote el código y el `state` correspondiente.

Luego, inyecte el código:

 1. Inicie el flujo de código de autorización con la usuaria Mallory e inyecte en el proceso los valores del código y `state` de la usuaria Alice obtenidos previamente.
 2. Si el ataque tiene éxito, el cliente debería tener ahora un `authorization_token` que otorgue acceso a los recursos propiedad de la usuaria Alice.

```http
GET /callback?code=INJECT_CODE_HERE&state=example HTTP/1.1
Host: client.example.com
[...]

```

### Ataque de degradación de PKCE

En determinadas circunstancias, la extensión PKCE puede eliminarse del flujo de código de autorización. Esto puede dejar a los clientes públicos vulnerables a ataques que la extensión PKCE mitiga.

Esto puede ocurrir cuando:

- El AS no admite PKCE.
- El AS no valida correctamente PKCE.

Ambos casos pueden probarse con un proxy de interceptación HTTP, como ZAP. Realice las siguientes pruebas:

1. Envíe la solicitud de autorización sin los parámetros `code_challenge=sha256(xyz)` y `code_challenge_method`.
2. Envíe la solicitud de autorización con un valor vacío para el parámetro `code_challenge=sha256(xyz)`.
3. Envíe la solicitud de autorización con un valor falsificado para el parámetro `code_challenge=sha256(xyz)`.

El siguiente ejemplo destaca los valores que se deben modificar:

```http
GET /authorize
    ?redirect_uri=http%3A%2F%client.example.com
    &client_id=example-client
    &errorPath=%2Ferror
    &scope=openid%20profile%20email
    &response_type=code
    &response_mode=web_message
    &state=example-state
    &nonce=example-nonce
    &code_challenge=MODIFY_OR_OMIT_THIS
    &code_challenge_method=MODIFY_OR_OMIT_THIS
    &prompt=none HTTP/1.1
Host: as.example.com
[...]

```

El AS debe verificar el valor de `code_verifier` durante el intercambio de token. Para probarlo:

1. Envíe la solicitud de token sin `code_verifier`.
2. Envíe la solicitud de token con un `code_verifier` vacío.
3. Envíe la solicitud de token con un `code_verifier` válido para otro código de autorización.

```http
POST /oauth/token HTTP/1.1
Host: as.example.com
[...]

{
"client_id":"example-client",
"code_verifier":"MODIFY_OR_OMIT_THIS",
"code":"example",
"grant_type":"authorization_code",
"redirect_uri":"https://client.example.com"
}
```

### Falsificación de solicitudes entre sitios en la página de consentimiento

Los ataques CSRF se describen en [CSRF](../06-Session_Management/05-Cross_Site_Request_Forgery.md). OAuth puede ser objeto de ataques CSRF.

Para prevenir ataques CSRF, OAuth utiliza el parámetro `state` como token anti-CSRF.

También pueden prevenir los ataques CSRF otras medidas. El flujo PKCE mitiga CSRF. Un valor `nonce` también puede actuar como token anti-CSRF.

Pruebe cada solicitud que contenga alguno de los parámetros anti-CSRF utilizados por OAuth, de acuerdo con las pruebas descritas en los casos de prueba de [CSRF](../06-Session_Management/05-Cross_Site_Request_Forgery.md).

La página de consentimiento se muestra al usuario para verificar que este consiente en que el cliente acceda al recurso en su nombre. Atacar la página de consentimiento mediante CSRF puede otorgar a un cliente arbitrario acceso a un recurso en nombre del usuario. Los pasos de este flujo son:

1. El cliente genera un parámetro `state` y lo envía con la solicitud de consentimiento.
2. El agente de usuario muestra la página de consentimiento.
3. El propietario del recurso otorga acceso al cliente.
4. El consentimiento se envía al AS junto con los ámbitos aceptados.

Utilice un proxy de interceptación HTTP, como ZAP, para comprobar si el parámetro `state` se valida correctamente.

```http
POST /u/consent?state=Tampered_State HTTP/1.1
Host: as.example.com
[...]

state=MODIFY_OR_OMIT_THIS
&audience=https%3A%2F%2Fas.example.com%2Fuserinfo
&scope%5B%5D=profile
&scope%5B%5D=email
&action=accept
```

### Clickjacking

El clickjacking se describe en [Clickjacking](../11-Client-side/09-Clickjacking.md). Si la página de consentimiento es vulnerable al clickjacking y el atacante conoce el `client_id` (en el caso de clientes públicos) o el secreto de cliente (en el caso de clientes confidenciales), puede falsificar el consentimiento del usuario y obtener acceso al recurso solicitado mediante un cliente malicioso.

#### Cómo probar

Para que este ataque tenga éxito, el atacante debe cargar la página de autorización en un iframe.

La siguiente página HTML puede utilizarse para cargar la página de autorización en un iframe:

```html
<html>
    <head>
        <title>Clickjack test page</title>
    </head>
    <body>
        <iframe src="https://as.example.com/auth/realms/example/login-actions/required-action?execution=OAUTH_GRANT&client_id=example-client" width="500" height="500"></iframe>
    </body>
</html>
```

Si se carga correctamente, el sitio es vulnerable al clickjacking.

Consulte [Clickjacking](../11-Client-side/09-Clickjacking.md) para obtener una descripción detallada de cómo se puede llevar a cabo este ataque.

### Tiempo de vida de los tokens

OAuth tiene dos tipos de tokens: el token de acceso y el token de actualización. La duración de la validez de un token de acceso debe ser limitada. Esto significa que debe tener una vida corta: una duración adecuada depende de la aplicación y puede ser de entre 5 y 15 minutos.

El token de actualización debe ser válido durante más tiempo. Debe ser un token de un solo uso que se reemplace cada vez que se utiliza.

#### Prueba de la validación del tiempo de vida del token de acceso

Cuando se utiliza un JSON Web Token (JWT) como token de acceso, es posible obtener la validez del token de acceso a partir del JWT decodificado. Esto se describe en [Pruebas de JSON Web Tokens](../06-Session_Management/10-JSON_Web_Tokens.md). Es posible que el AS no valide correctamente el tiempo de vida del JWT.

Para probar el tiempo de vida del token de acceso, utilice un proxy de interceptación HTTP, como ZAP. Intercepte una solicitud a un endpoint que contenga un token de acceso. Envíe esta solicitud al repetidor y espere a que transcurra el tiempo establecido. La validez de un token de acceso debería ser de entre 5 y 15 minutos, según la sensibilidad de los recursos.

Estas solicitudes pueden parecerse al siguiente ejemplo. El token también puede transmitirse de otras formas, por ejemplo, en una cookie.

```http
GET /userinfo HTTP/1.1
Host: as.example.com
[...]
Authorization: Bearer eyJhbGciOiJkaXIiL[...]

```

Pruebe la validación del tiempo de vida enviando la solicitud después de distintos intervalos, por ejemplo, después de 5, 10 y 30 minutos.

Este proceso puede optimizarse mediante la automatización de los pasos y el registro de la respuesta del servidor. Si se recibe una respuesta con estado HTTP 403 en lugar de HTTP 200, esto puede indicar que el token de acceso ya no es válido.

#### Prueba de la validación del tiempo de vida del token de actualización

Los tokens de actualización tienen un período de validez más largo que los tokens de acceso. Debido a su larga validez, deberían invalidarse después de utilizarlos en un intercambio por un token de acceso.

Los tokens de actualización se emiten en la misma solicitud de token en la que se entrega el token de acceso al cliente.

Utilice un proxy de interceptación HTTP, como ZAP. Prepare la prueba siguiendo estos pasos:

1. Obtenga un token de actualización válido.
2. Capture la solicitud utilizada para intercambiar el token de actualización por un nuevo token de acceso.
3. Envíe la solicitud capturada al repetidor de solicitudes.

En el siguiente ejemplo, el token de actualización se envía como parte del cuerpo de la solicitud POST.

```http
POST /token HTTP/1.1
Host: as.example.com
Cookie: [...]
[...]

grant_type=refresh_token
&refresh_token=eyJhbGciOiJIUz[...]
&client_id=example-client

```

Realice las siguientes pruebas:

1. Envíe el token de actualización y determine si el AS entrega un token de acceso.
2. Repita los pasos con el mismo token de actualización para evaluar cuántas veces se acepta un único token de actualización.

Cuando se utiliza un JWT como token de actualización, es posible obtener la validez del token de actualización a partir del JWT decodificado. Esto se describe en [Pruebas de JSON Web Tokens](../06-Session_Management/10-JSON_Web_Tokens.md). El token de actualización puede ser válido durante más tiempo, pero debe tener una fecha de expiración.

Se puede obtener seguridad adicional mediante un mecanismo de detección de robo. Si se utiliza un token de actualización en un intercambio por un token después de que haya caducado (o haya superado su tiempo de vida), el AS invalida todos los tokens de actualización. Para probar este mecanismo:

1. Envíe el token de actualización y determine si el AS entrega un token de acceso.
2. Repita los pasos con el mismo token de actualización hasta que se invalide.
3. Utilice el token de actualización de la última respuesta de token.

Si se invalidan todos los tokens de actualización emitidos al cliente para este propietario del recurso, el AS cuenta con detección de robo de tokens.

## Mitigación

La mayoría de los ataques contra el AS de OAuth pueden mitigarse validando la existencia y el contenido de los parámetros durante el intercambio del código de autorización y del token.

Restrinja el período de validez y los usos permitidos de credenciales como el código de autorización y el token de actualización. Esto puede mitigar algunos tipos de ataques y también limita el uso que un atacante puede hacer de dichas credenciales si las obtiene.

La configuración adecuada de medidas de seguridad, como CORS, los tokens anti-CSRF y los encabezados contra el clickjacking, puede mitigar los ataques o limitar su impacto.

- Valide siempre que estén presentes todos los parámetros y valide sus valores.
- Utilice la extensión PKCE para proteger correctamente el intercambio del código de autorización y del token.
- No permita mecanismos alternativos para funciones de seguridad como la extensión PKCE.
- Restrinja el tiempo de vida de las credenciales.
- Utilice las credenciales una sola vez siempre que sea posible; por ejemplo, el código de autorización.
- Configure las medidas de seguridad disponibles, como CORS, los tokens anti-CSRF y los encabezados contra el clickjacking.
