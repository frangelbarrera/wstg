# XSS basado en DOM propio

## Resumen

El XSS basado en DOM propio es un ataque específico que requiere conocimientos previos sobre el XSS basado en DOM y una ingeniería social exitosa. El término «propio» hace referencia al hecho de que el usuario debe inyectar el payload en el campo de entrada y, por tanto, ejecutar la vulnerabilidad por sí mismo. Esta vulnerabilidad también tiene la particularidad de que la Política de Seguridad de Contenido (CSP) del sitio web puede bloquear la ejecución de scripts.

En este contexto, se usará el término «sink» de la siguiente manera: en informática, un sink, event sink o data sink es una clase o función diseñada para recibir entradas o eventos de otro objeto o función. Por lo tanto, para encontrar posibles vulnerabilidades, primero debemos identificar los sinks de la aplicación que queremos probar.

## Cómo probar

El proceso para probar el XSS basado en DOM propio es el siguiente:

1. Buscar sinks vulnerables que permitan la entrada del usuario.
2. Una vez identificado un posible sink, se puede insertar un payload.
3. Revisar el registro de errores en las herramientas de desarrollo del navegador para ver el resultado y sacar conclusiones.
4. Comprobar si un atacante podría convencer a un usuario para que inserte el payload sin que se requieran conocimientos técnicos avanzados.

### Ejemplo

Este ejemplo específico proviene de este [informe de HackerOne](https://hackerone.com/reports/406587).

En el ejemplo, se ejecuta la siguiente función JavaScript en el sitio web `https://example.com`.

```js
//Marketo Form Code
function strip(html) {
    var tmp = document.createElement("DIV");
    tmp.innerHTML = html;
    return tmp.textContent || tmp.innerText || "";
}

$('form').submit(function() {
    $('textarea').val(function() {
        return strip($(this).val());
    });
});
```

El abuso de esta funcionalidad puede describirse de la siguiente manera:

1. El controlador del evento `submit` pasa el valor actual de cualquier elemento `textarea` a la función `strip`.
2. Esta función crea un nuevo elemento `div` y establece la propiedad `innerHTML` con el valor proporcionado.
3. Por último, devuelve la propiedad `textContent` del `div` resultante.

Este tipo de código suele usarse para eliminar etiquetas HTML de una cadena, ya que la propiedad `textContent` contiene la cadena que el navegador renderizó al analizar el HTML. Este método en particular es intrínsecamente inseguro porque usa `innerHTML`. Cuando se proporciona la entrada del usuario a la propiedad `innerHTML`, el navegador web la analiza y, por lo tanto, puede producirse la ejecución de JavaScript malicioso.

El siguiente payload puede usarse para probar la vulnerabilidad: `<img src=x onerror=alert(1) />`

La consola del desarrollador mostraría dos errores: uno que indica que se solicitó `https://www.example.com/x` y que la solicitud devolvió un error 404 (debido al atributo `src` de la etiqueta `img`), y otro que informa de una infracción de la CSP del sitio web.

Este segundo error se produjo porque el navegador intenta ejecutar el código JavaScript del atributo `onerror`, pero la CSP del sitio web impidió su ejecución. Al realizar las mismas acciones en un navegador con la CSP deshabilitada, se permitió la ejecución del JavaScript del atributo `onerror`.

Un atacante podría explotar esta vulnerabilidad convenciendo a un usuario para que pegue un payload malicioso en el campo «message» del formulario de contacto y luego haga clic en el botón «send message». El atacante podría potenciar este ataque convenciendo al usuario para que use una versión del navegador que no admita CSP.
