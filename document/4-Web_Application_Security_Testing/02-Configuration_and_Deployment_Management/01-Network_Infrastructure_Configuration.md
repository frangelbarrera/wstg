# Configuración de la infraestructura de red

|ID          |
|------------|
|WSTG-CONF-01|

## Resumen

La infraestructura de una aplicación web —servidores web y de aplicaciones, bases de datos, servidores de autenticación, balanceadores de carga/CDN y, en las implementaciones modernas, controles de red en la nube y capas de contenedores u orquestación— solo es tan segura como su elemento más débil y peor configurado. Un único componente vulnerable o que no se haya revisado puede comprometer la propia aplicación, aunque el código de la aplicación sea sólido; por ejemplo, un fallo del servidor web que divulgue el código fuente proporciona a un atacante información para atacar directamente la aplicación.

Después de mapear la infraestructura (véase [Mapear la arquitectura de red y de la aplicación](../01-Information_Gathering/10-Map_Application_Architecture.md)), las pruebas deben:

- Identificar cada elemento y cómo afecta a la seguridad de la aplicación.
- Revisar cada elemento para detectar vulnerabilidades conocidas.
- Revisar las herramientas administrativas utilizadas para mantenerlos.
- Revisar los sistemas de autenticación para detectar posibles manipulaciones por parte de usuarios externos.
- Mantener una lista de los puertos que requiere la aplicación y comprobarla bajo control de cambios.

## Objetivos de prueba

- Revisar las configuraciones de las aplicaciones establecidas en la red y validar que no sean vulnerables.
- Validar que los frameworks y sistemas utilizados sean seguros y no sean susceptibles a vulnerabilidades conocidas debido a software sin mantenimiento o a configuraciones y credenciales predeterminadas.
- Si la infraestructura está alojada en la nube o utiliza contenedores, revisar los controles de aislamiento de red (grupos de seguridad/NSG, diseño de VPC/subredes, configuración del balanceador de carga/CDN, políticas de service mesh y `NetworkPolicy` de Kubernetes) para detectar exposiciones involuntarias o reglas demasiado permisivas.

## Cómo probar

### Vulnerabilidades conocidas del servidor

Las vulnerabilidades en distintas áreas de la arquitectura de la aplicación, ya sea en el servidor web o en la base de datos backend, pueden comprometer gravemente la aplicación. Por ejemplo, consideremos una vulnerabilidad del servidor que permite a un usuario remoto no autenticado cargar archivos en el servidor web o incluso reemplazar archivos existentes. Esta vulnerabilidad podría comprometer la aplicación, ya que un usuario malicioso podría reemplazar la propia aplicación o introducir código que afectara a los servidores backend, pues el código de la aplicación se ejecutaría como cualquier otra aplicación.

Revisar las vulnerabilidades del servidor puede ser difícil si la prueba debe realizarse mediante una prueba de penetración a ciegas. En estos casos, las vulnerabilidades deben probarse desde un sitio remoto, normalmente mediante una herramienta automatizada. Sin embargo, probar algunas vulnerabilidades puede tener resultados impredecibles en el servidor web, y probar otras (como las relacionadas directamente con ataques de denegación de servicio) podría no ser posible debido al tiempo de inactividad del servicio que se produciría si la prueba tuviera éxito.

Algunas herramientas automatizadas señalarán vulnerabilidades según la versión del servidor web que detecten. Esto da lugar a falsos positivos y falsos negativos. Por un lado, si el administrador local del sitio ha eliminado u ocultado la versión del servidor web, la herramienta de análisis no lo señalará como vulnerable, aunque lo sea. Por otro lado, si el proveedor del software no actualiza la versión del servidor web cuando corrige vulnerabilidades, la herramienta señalará vulnerabilidades que no existen. Este último caso es bastante común, ya que algunos proveedores de sistemas operativos retroportan parches de vulnerabilidades de seguridad al software que incluyen en el sistema operativo, pero no lo actualizan por completo a la versión más reciente. Esto ocurre en la mayoría de las distribuciones GNU/Linux, como Debian, Red Hat y SuSE. En la mayoría de los casos, el análisis de vulnerabilidades de una arquitectura de aplicación solo encontrará vulnerabilidades asociadas con sus elementos «expuestos» (como el servidor web) y, por lo general, no podrá encontrar las asociadas con elementos que no están expuestos directamente, como el backend de autenticación, la base de datos backend o los proxies inversos en uso.

Por último, no todos los proveedores de software divulgan públicamente las vulnerabilidades, lo que significa que estas debilidades podrían no estar registradas en bases de datos de vulnerabilidades conocidas (como [NVD](https://nvd.nist.gov/) o los avisos específicos de los proveedores). Esta información solo se comunica a los clientes o se publica mediante correcciones que no incluyen avisos. Esto reduce la eficacia de las herramientas de análisis de vulnerabilidades. Por lo general, estas herramientas tendrán una cobertura muy buena para productos comunes (como el servidor web Apache, Microsoft IIS o IBM's Lotus Domino), pero será insuficiente para productos menos conocidos.

Por eso, lo mejor es revisar las vulnerabilidades cuando se proporciona al evaluador información interna sobre el software, incluidas las versiones, las ediciones y los parches aplicados. Con esta información, el evaluador puede obtener datos del proveedor y analizar las vulnerabilidades potenciales de la arquitectura, así como su posible impacto en la aplicación. Cuando sea posible, estas vulnerabilidades pueden probarse para determinar sus efectos reales y detectar si hay elementos externos (como sistemas de detección o prevención de intrusiones) que podrían reducir o anular la posibilidad de una explotación satisfactoria. Los evaluadores incluso podrían determinar mediante una revisión de la configuración que la vulnerabilidad no está realmente presente porque afecta a un componente de software que no está en uso.

También cabe señalar que, en ocasiones, los proveedores corrigen vulnerabilidades en silencio y ponen las correcciones a disposición junto con nuevas versiones del software. Los distintos proveedores tienen ciclos de publicación diferentes que determinan el soporte que ofrecen para las versiones anteriores. Un evaluador que disponga de información detallada sobre las versiones de software utilizadas por la arquitectura puede analizar el riesgo asociado al uso de versiones antiguas que podrían dejar de recibir soporte a corto plazo o que ya no lo reciben. Esto es fundamental porque, si surge una vulnerabilidad en una versión antigua del software que no recibe soporte, es posible que el personal de sistemas no tenga conocimiento directo de ella. Nunca se publicarán parches para esa versión y los avisos podrían no incluirla como vulnerable, ya que ha dejado de recibir soporte. Aunque conozcan la vulnerabilidad y los riesgos asociados para el sistema, será necesario actualizar por completo a una nueva versión del software, lo que podría provocar un tiempo de inactividad considerable en la arquitectura de la aplicación o requerir la recodificación de la aplicación debido a incompatibilidades con la versión más reciente del software.

### Configuración de red en la nube y de contenedores

El mismo principio de revisión de la configuración de red se aplica cuando la «infraestructura de red» se define en la configuración del proveedor de nube o en los manifiestos de contenedores u orquestación, en lugar de en routers, switches y firewalls físicos. Las configuraciones incorrectas son una de las causas más comunes de exposición involuntaria a Internet de sistemas que, de otro modo, serían internos. La tabla siguiente distingue lo que se puede comprobar sin credenciales (caja negra) de lo que requiere acceso a la configuración del proveedor (caja gris), e indica las pruebas que realmente respaldan un hallazgo: en todos estos casos, el resultado de caja negra (un puerto que responde o un servicio accesible) constituye la prueba; la configuración en sí, observada mediante caja gris, explica la causa.

| Control | Prueba de caja negra | Prueba de caja gris | Prueba necesaria para respaldar un hallazgo |
|---------|----------------|----------------|------------------------------|
| Grupos de seguridad / NSG / reglas de firewall en la nube | Analizar las IP públicas del objetivo en busca de puertos distintos de los que deben estar expuestos públicamente (en especial, puertos SSH/RDP/de bases de datos). | Leer directamente el conjunto de reglas: `aws ec2 describe-security-groups` (AWS), `az network nsg rule list --nsg-name <nsg>` (Azure) o `gcloud compute firewall-rules list` (GCP), y comprobar si hay tráfico entrante desde `0.0.0.0/0` o tráfico saliente sin restricciones. | El análisis de caja negra muestra que el puerto realmente responde (no solo que está filtrado o no responde), o el conjunto de reglas observado mediante caja gris muestra una regla específica que concede ese acceso sin controles compensatorios. |
| Aislamiento de VPC/subredes | Intentar acceder directamente desde Internet a los hosts del nivel backend (puertos de bases de datos, rutas administrativas internas) mediante direcciones o nombres de host encontrados durante el reconocimiento. | Revisar el diseño de la VPC/subredes y las tablas de enrutamiento: `aws ec2 describe-route-tables` (AWS), `az network vnet subnet list` y la inspección de las tablas de enrutamiento (Azure), o `gcloud compute networks subnets list` / `gcloud compute routes list` (GCP); confirmar que los niveles backend estén en subredes privadas sin rutas a una puerta de enlace de Internet. | La conexión directa desde fuera de la VPC tiene éxito, o la tabla de enrutamiento muestra una ruta a una puerta de enlace de Internet/NAT desde una subred que debería ser privada. |
| Configuración del balanceador de carga/CDN | Intentar acceder directamente al servidor de origen (eludiendo el nombre de host del balanceador de carga/CDN) mediante una IP encontrada en el historial de DNS, los registros de transparencia de certificados o encabezados filtrados. | Revisar las reglas de escucha, la configuración del origen y los ajustes de restricción del origen (por ejemplo, un grupo de seguridad del origen limitado únicamente a los rangos de IP de la CDN, o un encabezado secreto/de verificación del origen). | El origen responde al intento de elusión directa (no solo al tráfico que pasa por el nombre de host previsto del balanceador de carga/CDN). |
| Políticas de service mesh | En la mayoría de las implementaciones no se puede probar directamente desde fuera de la malla; indicarlo como una prueba solo de caja gris, salvo que el evaluador tenga acceso a un punto de apoyo dentro del clúster o la malla. | Para Istio: `kubectl get authorizationpolicy --all-namespaces` y `kubectl get peerauthentication --all-namespaces -o yaml` (comprobar `mtls.mode`) para revisar las políticas de autorización y el modo mTLS de los servicios que deberían requerir autenticación interna de la malla. | Se encuentra una política `ALLOW-ALL` o un modo mTLS `PERMISSIVE`/ausente en la configuración; idealmente, se confirma que una llamada no autenticada dentro de la malla tiene éxito cuando el diseño indicaba que debía denegarse. |
| `NetworkPolicy` de Kubernetes | Desde un pod que ya esté dentro del clúster (si está dentro del alcance), intentar una conexión desde un pod no autorizado a una carga de trabajo sensible (por ejemplo, un pod de base de datos). | Confirmar qué complemento CNI está instalado (`kubectl get pods -n kube-system` para identificar los pods propios del CNI, por ejemplo, `calico-node` o `cilium`) y si aplica `NetworkPolicy`; ejecutar `kubectl get networkpolicy --all-namespaces` y `kubectl describe networkpolicy <name> -n <namespace>` para revisar los objetos de políticas de la carga de trabajo sensible y comprobar si se aplica la denegación predeterminada a nivel de espacio de nombres. | El intento de conexión dentro del clúster tiene éxito a pesar de que parece haber una `NetworkPolicy` restrictiva (lo que demuestra que el CNI no la está aplicando), o `kubectl get networkpolicy` no devuelve nada para un espacio de nombres que contiene una carga de trabajo sensible. |

Hay algunos aspectos que conviene tener en cuenta y que se aplican a las cinco filas:

- Estas comprobaciones son ilustrativas, no exhaustivas: las llamadas a la API, los comandos CLI y las rutas de la consola exactos varían según el proveedor y la versión, y cambian con el tiempo. Adapte las comprobaciones a la implementación real (AWS, Azure o GCP; el complemento CNI y la service mesh utilizados), en lugar de tratar los comandos anteriores como universales.
- Los resultados de caja negra son la prueba principal de un hallazgo; la revisión de la configuración mediante caja gris explica la causa y ayuda a confirmar la corrección. Sin embargo, si una prueba de caja negra no reproduce la exposición (por ejemplo, el puerto está filtrado pese a que una regla parece permisiva porque otro control lo bloquea), hay que volver a delimitar el hallazgo, no concluir que la revisión de la configuración era incorrecta.

Por ejemplo: un grupo de seguridad que debía permitir que el balanceador de carga se comunicara con la aplicación por el puerto 443 también tiene una regla entrante que deja abierto el puerto 3306 (MySQL) a `0.0.0.0/0`; se añadió temporalmente para un script de migración puntual y nunca se eliminó.

### Herramientas administrativas

Toda infraestructura de servidor web requiere herramientas administrativas para mantener y actualizar la información que utiliza la aplicación. Esta información incluye contenido estático (páginas web, archivos gráficos), código fuente de la aplicación, bases de datos de autenticación de usuarios, etc. El tipo de herramientas administrativas utilizadas puede variar según el sitio, la tecnología o el software específicos: algunas son consolas administrativas web (véase también [Enumerar las interfaces administrativas de la infraestructura y de la aplicación](05-Enumerate_Infrastructure_and_Application_Admin_Interfaces.md), donde se trata el tema con más detalle, incluidas las consolas modernas de nube, Kubernetes y CI/CD); otras son archivos de configuración de texto plano (como en Apache), y otras son herramientas gráficas o de línea de comandos nativas del sistema operativo (como en el servidor IIS de Microsoft o `kubectl`/las CLI de nube en las implementaciones modernas).

En la mayoría de los casos, la configuración del servidor se gestiona con distintas herramientas de mantenimiento de archivos, administradas mediante SSH/SFTP, WebDAV, sistemas de archivos de red (NFS, CIFS), procesos de infraestructura como código (Terraform/CloudFormation/Ansible) o herramientas de GitOps que aplican automáticamente los cambios de configuración. Obviamente, el sistema operativo de los elementos que componen la arquitectura de la aplicación también se gestionará mediante otras herramientas. Las aplicaciones también pueden incluir interfaces administrativas integradas para gestionar datos de la aplicación (usuarios, contenido, etc.).

Después de mapear las interfaces administrativas utilizadas para gestionar las distintas partes de la arquitectura, es importante revisarlas. Si un atacante obtiene acceso a cualquiera de estas interfaces, podría comprometer o dañar la arquitectura de la aplicación. Para ello, es importante:

- Determinar los mecanismos que controlan el acceso a estas interfaces y sus vulnerabilidades asociadas. Esta información podría estar disponible en línea.
- Asegurarse de cambiar el nombre de usuario y la contraseña predeterminados.

Algunas empresas deciden no gestionar todos los aspectos de sus aplicaciones de servidor web y pueden delegar la gestión del contenido a terceros. Esta empresa externa podría proporcionar solo ciertas partes del contenido (como actualizaciones de noticias o promociones), o gestionar por completo el servidor web (incluidos el contenido y el código). En estas situaciones es común encontrar interfaces administrativas accesibles desde Internet, ya que usar Internet es más barato que proporcionar una línea dedicada que conecte a la empresa externa con la infraestructura de la aplicación mediante una interfaz exclusiva para la gestión. En tales situaciones, es fundamental probar si las interfaces administrativas son vulnerables a ataques.

## Herramientas

- [nmap](https://nmap.org/) - análisis de redes y puertos, e identificación de servicios.
- [ScoutSuite](https://github.com/nccgroup/ScoutSuite) - auditoría de la configuración de seguridad en múltiples nubes (AWS/Azure/GCP), incluidos los grupos de seguridad/NSG y la exposición de red.
- [Prowler](https://github.com/prowler-cloud/prowler) - evaluación de seguridad de AWS/Azure/GCP, incluidas las comprobaciones de reglas de red y firewall.
- [kube-bench](https://github.com/aquasecurity/kube-bench) - herramienta de análisis del CIS Kubernetes Benchmark.
- [kube-hunter](https://github.com/aquasecurity/kube-hunter) - identifica componentes de Kubernetes expuestos a la red.
- [Shodan](https://www.shodan.io/) / [Censys](https://censys.com/) - datos de análisis de Internet a escala global útiles para identificar infraestructuras expuestas involuntariamente durante evaluaciones de caja negra.
