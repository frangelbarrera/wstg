# MySQL

## Resumen

Las vulnerabilidades de [inyección SQL](https://owasp.org/www-community/attacks/SQL_Injection) se producen cuando se utiliza una entrada para construir una consulta SQL sin restringirla ni sanearla adecuadamente. El uso de SQL dinámico (la construcción de consultas SQL mediante la concatenación de cadenas) abre la puerta a estas vulnerabilidades. La inyección SQL permite que un atacante acceda a los servidores SQL y ejecute código SQL con los privilegios del usuario utilizado para conectarse a la base de datos.

El *servidor MySQL* tiene algunas particularidades que hacen necesario adaptar específicamente algunos exploits a esta aplicación. Este es el tema de esta sección. Como MariaDB es una bifurcación de MySQL, el contenido de esta página también es pertinente para MariaDB.

## Cómo probar

Cuando se encuentra una vulnerabilidad de inyección SQL en una aplicación respaldada por una base de datos MySQL, se pueden realizar distintos ataques, según la versión de MySQL y los privilegios del usuario en el SGBD.

MySQL tiene al menos cuatro versiones que se usan en entornos de producción de todo el mundo: `3.23.x`, `4.0.x`, `4.1.x` y `5.0.x`. Cada versión ofrece un conjunto de funcionalidades proporcional a su número de versión.

- Desde la versión 4.0: UNION
- Desde la versión 4.1: subconsultas
- Desde la versión 5.0: procedimientos almacenados, funciones almacenadas y la vista llamada `INFORMATION_SCHEMA`
- Desde la versión 5.0.2: desencadenadores

Cabe señalar que, en las versiones de MySQL anteriores a la 4.0.x, solo se podían utilizar ataques de inyección ciega booleana o basada en tiempo, ya que no se habían implementado la funcionalidad de subconsultas ni las instrucciones `UNION`.

A partir de aquí, supondremos que existe una vulnerabilidad clásica de inyección SQL, que puede activarse mediante una solicitud similar a la descrita en la sección sobre [inyección SQL](05-SQL_Injection.md).

`https://www.example.com/page.php?id=2`

### El problema de las comillas simples

Antes de aprovechar las funcionalidades de MySQL, hay que tener en cuenta cómo se representan las cadenas en una instrucción, ya que las aplicaciones web suelen escapar las comillas simples.

El escape de comillas de MySQL es el siguiente:

`'Una cadena con \'comillas\''`

Es decir, MySQL interpreta las comillas simples escapadas `\'` como caracteres y no como metacaracteres.

Por lo tanto, si la aplicación necesita utilizar cadenas constantes para funcionar correctamente, hay que distinguir dos casos:

1. La aplicación web escapa las comillas simples `'` => `\'`
2. La aplicación web no escapa las comillas simples `'` => `'`

En MySQL, existe una forma estándar de evitar la necesidad de usar comillas simples: declarar una cadena constante sin ellas.

Supongamos que queremos conocer el valor de un campo llamado `password` en un registro, con una condición como la siguiente:

1. password like `'A%'`
2. Los valores ASCII representados en hexadecimal concatenado:
    `password LIKE 0x4125`
3. La función `CHAR()`:
    `password LIKE CHAR(65,37)`

### Consultas mixtas múltiples

Los conectores de bibliotecas de MySQL no admiten varias consultas separadas por `;`, por lo que no hay forma de inyectar varios comandos SQL heterogéneos en una única vulnerabilidad de inyección SQL, como sí es posible en Microsoft SQL Server.

Por ejemplo, la siguiente inyección provocará un error:

`1 ; update tablename set code='javascript code' where 1 --`

### Recopilación de información

#### Identificación de MySQL

Lo primero que hay que averiguar es si MySQL es el SGBD de la base de datos backend. El servidor MySQL tiene una funcionalidad que permite que otros SGBD ignoren una cláusula del dialecto de MySQL. Cuando un bloque de comentario `'/**/'` contiene un signo de exclamación, como en `'/*! sql here*/'`, MySQL lo interpreta, mientras que otros SGBD lo consideran un bloque de comentario normal, tal como se explica en el [manual de MySQL](https://dev.mysql.com/doc/refman/8.0/en/comments.html).

Ejemplo:

`1 /*! and 1=0 */`

> Si MySQL está presente, se interpretará la cláusula dentro del bloque de comentario.

#### Versión

Hay tres formas de obtener esta información:

1. Mediante la variable global `@@version`
2. Mediante la función [VERSION()](https://dev.mysql.com/doc/refman/8.0/en/information-functions.html#function_version)
3. Mediante la identificación con comentarios y un número de versión `/*!40110 and 1=0*/`

lo que significa que

```sql
if(version >= 4.1.10)
   add 'and 1=0' to the query.
```

Son equivalentes, ya que el resultado es el mismo.

Inyección en banda:

`1 AND 1=0 UNION SELECT @@version /*`

Inyección inferencial:

`1 AND @@version like '4.0%'`

La respuesta contendría algo parecido a:

`5.0.22-log`

#### Usuario de inicio de sesión

MySQL Server utiliza dos tipos de usuarios.

1. [USER()](https://dev.mysql.com/doc/refman/8.0/en/information-functions.html#function_user): el usuario conectado a MySQL Server.
2. [CURRENT_USER()](https://dev.mysql.com/doc/refman/8.0/en/information-functions.html#function_current-user): el usuario interno que ejecuta la consulta.

Hay diferencias entre ambos. La principal es que un usuario anónimo puede conectarse (si se permite) con cualquier nombre, pero el usuario interno de MySQL tiene un nombre vacío (''). Otra diferencia es que los procedimientos almacenados y las funciones almacenadas se ejecutan con el usuario que los creó, salvo que se indique lo contrario. Esto puede averiguarse mediante `CURRENT_USER`.

Inyección en banda:

`1 AND 1=0 UNION SELECT USER()`

Inyección inferencial:

`1 AND USER() like 'root%'`

La respuesta contendría algo parecido a:

`user@hostname`

#### Nombre de la base de datos en uso

Existe la función nativa `DATABASE()`.

Inyección en banda:

`1 AND 1=0 UNION SELECT DATABASE()`

Inyección inferencial:

`1 AND DATABASE() like 'db%'`

> Resultado esperado: una cadena como esta:
>
> `dbname`

#### INFORMATION_SCHEMA

A partir de MySQL 5.0, se creó una vista llamada [INFORMATION_SCHEMA](https://dev.mysql.com/doc/refman/8.0/en/information-schema.html). Permite obtener toda la información sobre bases de datos, tablas y columnas, así como sobre procedimientos y funciones.

| Tables_in_INFORMATION_SCHEMA | DESCRIPTION |
|------------------------------|-------------|
| SCHEMATA  | Todas las bases de datos para las que el usuario tiene, como mínimo, el privilegio SELECT_priv |
| SCHEMA_PRIVILEGES  | Los privilegios que tiene el usuario para cada base de datos |
| TABLES  | Todas las tablas para las que el usuario tiene, como mínimo, el privilegio SELECT_priv |
| TABLE_PRIVILEGES | Los privilegios que tiene el usuario para cada tabla |
| COLUMNS | Todas las columnas para las que el usuario tiene, como mínimo, el privilegio SELECT_priv |
| COLUMN_PRIVILEGES | Los privilegios que tiene el usuario para cada columna |
| VIEWS | Todas las columnas para las que el usuario tiene, como mínimo, el privilegio SELECT_priv |
| ROUTINES | Procedimientos y funciones (requiere EXECUTE_priv) |
| TRIGGERS | Desencadenadores (requiere INSERT_priv) |
| USER_PRIVILEGES | Privilegios del usuario conectado |

Toda esta información puede extraerse mediante técnicas conocidas, como se describe en la sección sobre inyección SQL.

### Vectores de ataque

#### Escribir en un archivo

Si el usuario conectado tiene privilegios `FILE` y las comillas simples no están escapadas, se puede utilizar la cláusula `into outfile` para exportar los resultados de una consulta a un archivo.

`Select * from table into outfile '/tmp/file'`

> Nota: no hay forma de evitar las comillas simples que rodean el nombre de archivo. Por lo tanto, si se aplica algún saneamiento de las comillas simples, como escaparlas con `\'`, no se podrá utilizar la cláusula `into outfile`.

Este tipo de ataque puede utilizarse como técnica fuera de banda para obtener información sobre los resultados de una consulta o para escribir un archivo que podría ejecutarse dentro del directorio del servidor web.

Ejemplo:

`1 limit 1 into outfile '/var/www/root/test.jsp' FIELDS ENCLOSED BY '//'  LINES TERMINATED BY '\n<%jsp code here%>';`

> Los resultados se guardan en un archivo con permisos `rw-rw-rw`, propiedad del usuario y del grupo de MySQL.
>
> El archivo `/var/www/root/test.jsp` contendrá:
>
> `//field values//`
> `<%jsp code here%>`

#### Leer desde un archivo

`load_file` es una función nativa que puede leer un archivo si los permisos del sistema de archivos lo permiten. Si el usuario conectado tiene privilegios `FILE`, se puede utilizar para obtener el contenido de los archivos. Es posible eludir el saneamiento de las comillas simples escapadas mediante las técnicas descritas anteriormente.

`load_file('filename')`

> El archivo completo estará disponible para su exportación mediante técnicas estándar.

### Ataque de inyección SQL estándar

En una inyección SQL estándar, los resultados pueden mostrarse directamente en una página como salida normal o como error de MySQL. Mediante los ataques de inyección SQL ya mencionados y las funcionalidades de MySQL descritas anteriormente, se puede llevar a cabo fácilmente una inyección SQL directa. El grado de profundidad dependerá principalmente de la versión de MySQL a la que se enfrente el pentester.

Un buen método para conocer los resultados consiste en provocar un error en una función, un procedimiento o el propio servidor. En el [manual de MySQL](https://dev.mysql.com/doc/mysql-errors/8.0/en/server-error-reference.html) se puede encontrar una lista de errores generados por MySQL, en particular por sus funciones nativas.

### Inyección SQL fuera de banda

La inyección fuera de banda se puede llevar a cabo mediante la cláusula [`into outfile`](#write-in-a-file).

### Inyección SQL ciega

Para la inyección SQL ciega, el servidor MySQL proporciona de forma nativa varias funciones útiles.

- Longitud de una cadena:
    - `LENGTH(str)`
- Extraer una subcadena de una cadena dada:
    - `SUBSTRING(string, offset, #chars_returned)`
- Inyección ciega basada en tiempo:
    - BENCHMARK y SLEEP `BENCHMARK(#ofcycles,action_to_be_performed)`
    La función BENCHMARK puede utilizarse para realizar ataques de temporización cuando la inyección ciega basada en valores booleanos no da ningún resultado.
    Véase `SLEEP()` (MySQL > 5.0.x) como alternativa a BENCHMARK.

Para obtener una lista completa, consulte el [manual de MySQL](https://dev.mysql.com/doc/refman/8.0/en/functions.html)
