# Inyección NoSQL

## Resumen

Las bases de datos NoSQL ofrecen restricciones de consistencia más laxas que las bases de datos SQL tradicionales. Al requerir menos restricciones relacionales y comprobaciones de consistencia, las bases de datos NoSQL suelen ofrecer beneficios de rendimiento y escalabilidad. Sin embargo, estas bases de datos siguen siendo potencialmente vulnerables a ataques de inyección, aunque no utilicen la sintaxis SQL tradicional. Como estos ataques de inyección NoSQL pueden ejecutarse dentro de un [lenguaje procedimental](https://en.wikipedia.org/wiki/Procedural_programming), en lugar de hacerlo en el [lenguaje declarativo SQL](https://en.wikipedia.org/wiki/Declarative_programming), sus impactos potenciales son mayores que los de la inyección SQL tradicional.

Las llamadas a bases de datos NoSQL se escriben en el lenguaje de programación de la aplicación, se realizan mediante una llamada API personalizada o se formatean según una convención común (como `XML`, `JSON`, `LINQ`, etc.). La entrada maliciosa dirigida a esas especificaciones puede no activar las comprobaciones de sanitización que realiza principalmente la aplicación. Por ejemplo, filtrar caracteres especiales comunes de HTML como `< > & ;` no evitará ataques contra una API JSON, donde los caracteres especiales incluyen `/ { } :`.

Hay cientos de bases de datos NoSQL disponibles para su uso en aplicaciones, que proporcionan APIs en diversos lenguajes y modelos de relaciones. Cada una ofrece distintas características y restricciones. Como no existe un lenguaje común entre ellas, los ejemplos de código de inyección no se aplican a todas las bases de datos NoSQL. Por esta razón, quienes prueben ataques de inyección NoSQL deberán familiarizarse con la sintaxis, el modelo de datos y el lenguaje de programación subyacente para elaborar pruebas específicas.

Los ataques de inyección NoSQL pueden ejecutarse en áreas de la aplicación distintas de aquellas en las que se ejecuta la inyección SQL tradicional. Mientras que la inyección SQL se ejecutaría dentro del motor de la base de datos, las variantes NoSQL pueden ejecutarse en la capa de aplicación o en la capa de base de datos, según la API NoSQL utilizada y el modelo de datos. Por lo general, los ataques de inyección NoSQL se ejecutan donde la cadena de ataque se analiza, evalúa o concatena en una llamada a la API NoSQL.

Otros ataques de tiempo pueden ser pertinentes debido a la falta de comprobaciones de concurrencia en las bases de datos NoSQL. Estos no se abordan en las pruebas de inyección. En el momento de redactar este documento, MongoDB es la base de datos NoSQL más utilizada, por lo que todos los ejemplos se basan en APIs de MongoDB.

## Cómo probar

### Vulnerabilidades de inyección NoSQL en MongoDB

La API de MongoDB espera llamadas BSON (JSON binario) e incluye una herramienta segura para ensamblar consultas BSON. Sin embargo, según la documentación de MongoDB, se permiten JSON no serializado y [expresiones JavaScript](https://docs.mongodb.org/manual/faq/developers/#javascript) en varios parámetros de consulta alternativos. La llamada a la API más utilizada que permite introducir JavaScript arbitrario es el operador `$where`.

El operador `$where` de MongoDB suele utilizarse como un filtro o una comprobación simples, al igual que en SQL.

`db.myCollection.find( { $where: "this.credits`` ``==`` ``this.debits" } );`

También es posible evaluar JavaScript para permitir condiciones más avanzadas.

`db.myCollection.find( { $where: function() { return obj.credits - obj.debits < 0; } } );`

### Ejemplo 1

Si un atacante pudiera manipular los datos pasados al operador `$where`, podría incluir JavaScript arbitrario para que se evaluara como parte de la consulta de MongoDB. El siguiente código muestra una vulnerabilidad que puede producirse si la entrada del usuario se pasa directamente a la consulta de MongoDB sin sanitizarla.

`db.myCollection.find( { active: true, $where: function() { return obj.credits - obj.debits < $userInput; } } );;`

Al igual que al probar otros tipos de inyección, no es necesario explotar por completo la vulnerabilidad para demostrar que existe un problema. Al inyectar caracteres especiales pertinentes para el lenguaje de la API objetivo y observar los resultados, quien realiza las pruebas puede determinar si la aplicación sanitizó correctamente la entrada. Por ejemplo, en MongoDB, si se pasara sin sanitizar una cadena que contuviera cualquiera de los siguientes caracteres especiales, se produciría un error de base de datos.

`' " \ ; { }`

Con la inyección SQL normal, una vulnerabilidad similar permitiría a un atacante ejecutar comandos SQL arbitrarios y exponer o manipular datos a voluntad. Sin embargo, como JavaScript es un lenguaje con todas las funcionalidades, esto no solo permite a un atacante manipular datos, sino también ejecutar código arbitrario. Por ejemplo, en lugar de limitarse a provocar un error durante las pruebas, una explotación completa utilizaría los caracteres especiales para elaborar JavaScript válido.

La siguiente entrada `0;var date=new Date(); do{curDate = new Date();}while(curDate-date<10000)`, insertada en `$userInput` en el código de ejemplo anterior, haría que se ejecutara la siguiente función JavaScript. Esta cadena de ataque específica haría que toda la instancia de MongoDB funcionara al 100 % de uso de CPU durante 10 segundos.

`function() { return obj.credits - obj.debits < 0;var date=new Date(); do{curDate = new Date();}while(curDate-date<10000); }`

### Ejemplo 2

Aunque la entrada utilizada en las consultas se sanitice o parametrice por completo, existe otra vía que podría desencadenar una inyección NoSQL. Muchas instancias NoSQL tienen sus propios nombres de variables reservados, independientes del lenguaje de programación de la aplicación.

Por ejemplo, en MongoDB, la sintaxis `$where` es en sí misma un operador de consulta reservado. Debe pasarse a la consulta exactamente como se muestra; cualquier modificación provocaría un error de base de datos. Sin embargo, como `$where` también es un nombre de variable PHP válido, un atacante podría insertar código en la consulta creando una variable PHP llamada `$where`. La documentación de MongoDB para PHP advierte explícitamente a los desarrolladores:

> Asegúrese de utilizar comillas simples para todos los operadores de consulta especiales (que comienzan con `$`), de modo que PHP no intente reemplazar `$exists` por el valor de la variable `$exists`.

Aunque una consulta no dependiera de ninguna entrada del usuario, como en el siguiente ejemplo, un atacante podría explotar MongoDB reemplazando el operador por datos maliciosos.

`db.myCollection.find( { $where: function() { return obj.credits - obj.debits < 0; } } );`

Una posible forma de asignar datos a variables PHP es mediante la contaminación de parámetros HTTP (véase: [Contaminación de parámetros HTTP](04-HTTP_Parameter_Pollution.md)). Al crear una variable llamada `$where` mediante la contaminación de parámetros, se podría provocar un error de MongoDB que indicara que la consulta ya no es válida. Cualquier valor de `$where` distinto de la propia cadena `$where` debería bastar para demostrar la vulnerabilidad. Un atacante desarrollaría una explotación completa insertando lo siguiente:

`$where: function() { //JavaScript arbitrario aquí }`
