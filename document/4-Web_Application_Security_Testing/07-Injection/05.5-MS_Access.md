# MS Access

## Resumen

Como se explica en la sección genérica de [inyección SQL](https://owasp.org/www-community/attacks/SQL_Injection), las vulnerabilidades de inyección SQL se producen cuando se utiliza la entrada proporcionada por el usuario al construir una consulta SQL sin restringirla ni sanitizarla adecuadamente. Esta clase de vulnerabilidades permite que un atacante ejecute código SQL con los privilegios del usuario que se utiliza para conectarse a la base de datos. En esta sección se analizan técnicas relevantes de inyección SQL que utilizan características específicas de [Microsoft Access](https://en.wikipedia.org/wiki/Microsoft_Access).

## Cómo probar

### Identificación de huellas

La identificación de la tecnología de base de datos específica al probar aplicaciones que utilizan SQL es el primer paso para evaluar correctamente las posibles vulnerabilidades. Un enfoque común consiste en inyectar patrones estándar de ataque de inyección SQL (por ejemplo, una comilla simple, una comilla doble, ...) para provocar excepciones de la base de datos. Si la aplicación no gestiona las excepciones con páginas personalizadas, es posible identificar el DBMS subyacente observando los mensajes de error.

Según la tecnología web específica utilizada, las aplicaciones basadas en MS Access responderán con uno de los siguientes errores:

`Fatal error: Uncaught exception 'com_exception' with message Source: Microsoft JET Database Engine`

o

`Microsoft JET Database Engine error '80040e14'`

o

`Microsoft Office Access Database Engine`

En todos los casos, tenemos la confirmación de que estamos probando una aplicación que utiliza una base de datos MS Access.

### Pruebas básicas

Desafortunadamente, MS Access no admite operadores típicos que se utilizan tradicionalmente durante las pruebas de inyección SQL, entre ellos:

- No admite caracteres de comentario
- No admite consultas apiladas
- No admite el operador LIMIT
- No admite operadores como SLEEP o BENCHMARK
- y muchos otros

Sin embargo, es posible emular esas funciones combinando varios operadores o utilizando técnicas alternativas. Como se mencionó, no es posible utilizar el truco de insertar los caracteres `/*`, `--` o `#` para truncar la consulta. Afortunadamente, podemos eludir esta limitación inyectando un carácter nulo. El uso de un byte nulo `%00` dentro de una consulta SQL hace que MS Access ignore todos los caracteres restantes. Esto se explica porque, en la representación interna que utiliza la base de datos, todas las cadenas terminan en NULL. Cabe mencionar que el carácter `null` también puede causar problemas, ya que podría truncar las cadenas en el nivel del servidor web. En esas situaciones, sin embargo, podemos emplear otro carácter: `0x16` (`%16` en formato codificado para URL).

Consideremos la siguiente consulta:

`SELECT [username],[password] FROM users WHERE [username]='$myUsername' AND [password]='$myPassword'`

Podemos truncar la consulta con las siguientes dos URL:

- `https://www.example.com/page.asp?user=admin'%00&pass=foo`
- `https://www.example.com/page.app?user=admin'%16&pass=foo`

El operador `LIMIT` no está implementado en MS Access; sin embargo, es posible limitar el número de resultados utilizando en su lugar los operadores `TOP` o `LAST`.

`https://www.example.com/page.app?id=2'+UNION+SELECT+TOP+3+name+FROM+appsTable%00`

Combinando ambos operadores, es posible seleccionar resultados específicos. La concatenación de cadenas se puede realizar utilizando los caracteres `& (%26)` y `+ (%2b)`.

También hay muchas otras funciones que se pueden utilizar durante las pruebas de inyección SQL, entre ellas:

- ASC: Obtiene el valor ASCII de un carácter pasado como entrada
- CHR: Obtiene el carácter correspondiente al valor ASCII pasado como entrada
- LEN: Devuelve la longitud de la cadena pasada como parámetro
- IIF: Es la construcción IF; por ejemplo, la siguiente instrucción `IIF(1=1, 'a', 'b')` devuelve `a`
- MID: Esta función permite extraer subcadenas; por ejemplo, la siguiente instrucción `mid('abc',1,1)` devuelve `a`
- TOP: Esta función permite especificar el número máximo de resultados que debe devolver la consulta, comenzando por el primero. Por ejemplo, `TOP 1` devolverá solo 1 fila.
- LAST: Esta función se utiliza para seleccionar únicamente la última fila de un conjunto. Por ejemplo, la siguiente consulta `SELECT last(*)` FROM users devolverá solo la última fila del resultado.

Algunos de estos operadores son esenciales para explotar inyecciones SQL ciegas. Para otros operadores avanzados, consulta los documentos de las referencias.

#### Enumeración de atributos

Para enumerar las columnas de una tabla de base de datos, es posible utilizar una técnica común basada en errores. En resumen, podemos obtener los nombres de los atributos analizando los mensajes de error y repitiendo la consulta con distintos selectores. Por ejemplo, suponiendo que conocemos la existencia de una columna, también podemos obtener los nombres de los atributos restantes con la siguiente consulta:

`' GROUP BY Id%00`

En el mensaje de error recibido, es posible observar el nombre de la siguiente columna. En este punto, podemos repetir el método hasta obtener los nombres de todos los atributos. Si no conocemos el nombre del primer atributo, podemos insertar igualmente un nombre de columna ficticio y obtener el nombre del primer atributo en el mensaje de error.

#### Obtención del esquema de la base de datos

MS Access incluye varias tablas del sistema de forma predeterminada que podrían utilizarse para obtener nombres de tablas y columnas. Desafortunadamente, en la configuración predeterminada de las versiones recientes de las bases de datos MS Access, estas tablas no son accesibles. Sin embargo, siempre vale la pena intentarlo:

- MSysObjects
- MSysACEs
- MSysAccessXML

Por ejemplo, si existe una vulnerabilidad de inyección SQL de unión, puedes utilizar la siguiente consulta:

`' UNION SELECT Name FROM MSysObjects WHERE Type = 1%00`

Como alternativa, siempre es posible aplicar fuerza bruta al esquema de la base de datos utilizando una lista de palabras estándar (por ejemplo, [FuzzDb](https://github.com/fuzzdb-project/fuzzdb)).

En algunos casos, los desarrolladores o administradores del sistema no se dan cuenta de que incluir el archivo `.mdb` real en el directorio webroot de la aplicación puede permitir descargar toda la base de datos. Los nombres de los archivos de base de datos se pueden inferir con la siguiente consulta:

`https://www.example.com/page.app?id=1'+UNION+SELECT+1+FROM+name.table%00`

donde `name` es el nombre del archivo `.mdb` y `table` es una tabla válida de la base de datos. En el caso de las bases de datos protegidas por contraseña, se pueden utilizar varias herramientas de software para descifrarla. Consulta las referencias.

### Pruebas de inyección SQL ciega

Las vulnerabilidades de [inyección SQL ciega](https://owasp.org/www-community/attacks/Blind_SQL_Injection) no son, ni mucho menos, las inyecciones SQL más fáciles de explotar al probar aplicaciones en situaciones reales. En el caso de las versiones recientes de MS Access, tampoco es viable ejecutar comandos de shell ni leer o escribir archivos arbitrarios.

En el caso de las inyecciones SQL ciegas, el atacante solo puede inferir el resultado de la consulta evaluando las diferencias de tiempo o las respuestas de la aplicación. Se supone que el lector ya conoce la teoría de los ataques de inyección SQL ciega, ya que el resto de esta sección se centra en detalles específicos de MS Access.

Se utiliza el siguiente ejemplo:

`https://www.example.com/index.php?myId=[sql]`

donde el parámetro ID se utiliza en la siguiente consulta:

`SELECT * FROM orders WHERE [id]=$myId`

Consideremos que el parámetro `myId` es vulnerable a la inyección SQL ciega. Como atacantes, queremos extraer el contenido de la columna `username` de la tabla `users`, suponiendo que ya hemos descubierto el esquema de la base de datos.

Una consulta típica que se puede utilizar para inferir el primer carácter del nombre de usuario de la décima fila es:

`https://www.example.com/index.php?id=IIF((select%20MID(LAST(username),1,1)%20from%20(select%20TOP%2010%20username%20from%20users)='a',0,'no')`

Si el primer carácter es `a`, la consulta devolverá `0`; de lo contrario, devolverá la cadena `no`.

Mediante una combinación de las funciones `IFF, MID, LAST` y `TOP`, es posible extraer el primer carácter del nombre de usuario de una fila seleccionada específicamente. Como la consulta interna devuelve un conjunto de registros, y no solo uno, no es posible utilizarla directamente. Afortunadamente, podemos combinar varias funciones para extraer una cadena específica.

Supongamos que queremos recuperar el nombre de usuario de la décima fila. Primero, podemos utilizar la función TOP para seleccionar las diez primeras filas con la siguiente consulta:

`SELECT TOP 10 username FROM users`

Luego, utilizando este subconjunto, podemos extraer la última fila mediante la función LAST. Una vez que tenemos una sola fila, concretamente la que contiene nuestra cadena, podemos utilizar las funciones IFF, MID y LAST para inferir el valor real del nombre de usuario. En nuestro ejemplo, empleamos IFF para devolver un número o una cadena. Con este truco, podemos distinguir si la respuesta es verdadera o no observando los errores de la aplicación. Como `id` es numérico, la comparación con una cadena provoca un error SQL que podría filtrarse mediante páginas `500 Internal Server Error`. De lo contrario, probablemente se devolverá una página estándar `200 OK`.

Por ejemplo, podemos utilizar la siguiente consulta:

`https://www.example.com/index.php?id='%20AND%201=0%20OR%20'a'=IIF((select%20MID(LAST(username),1,1)%20from%20(select%20TOP%2010%20username%20from%20users))='a','a','b')%00`

que es TRUE si el primer carácter es 'a' y FALSE en caso contrario.

Como se mencionó, este método permite inferir el valor de cadenas arbitrarias dentro de la base de datos:

1. Probando todos los valores imprimibles hasta encontrar una coincidencia
2. Infiriendo la longitud de la cadena mediante la función `LEN` o, simplemente, deteniéndose después de encontrar todos los caracteres

También es posible realizar inyecciones SQL ciegas basadas en tiempo aprovechando [consultas pesadas](https://learn.microsoft.com/en-us/previous-versions/tn-archive/cc512676(v=technet.10)).
